### Second round, new issue N1 (low): the automatic linker overrides a rule's "not a transfer" and leaves the row in a state the next rules run reverses

Status: fixed.

What was wrong: `markAsTransfers` (`packages/db/src/services/transfers.ts`), called by the linker through `markLinkedCashTransfers` and by the trade import, set `is_transfer` on every linked bank row that was not a transfer, without looking at `not_transfer`. That column came later (audit a10-conformance-ledger-03, Phase 1 decision 106: a rule's "not a transfer" holds over automatic pairing). A5 says the linker marks the bank row "exactly as pairing marks its legs", and pairing skips such rows. So a brokerage deposit "MONEYLINK TXN FROM CHK 1234" that the household's rule ruled out became a transfer when the trade history's deposit linked to it (`is_transfer` true, `not_transfer` true, the linked goal's September 5,000.00), and the next rules run made it not a transfer again (the goal's September 0): the goal changed with whether rules had run since the last import or sync. The trade import did the same to the ledger rows it writes for the cash rows of an account without a feed (`update(transaction).set({ isTransfer: true, categoryId: null })` on `stats.insertedIds`, right after the rules ran on them). Separately, the linker marked rows the household categorized by hand (`category_locked`), which pairing never takes (decision 48: automation never overrides a hand categorization); a transfer leaves the plan's actuals, so the hand-categorized row left the plan.

The reviewer's evidence holds: with the code before the fix, the new db test's first case failed on the ruled-out row (`isTransfer: true` with `notTransfer: true` right after the link), and a run with only the category guard removed failed on the hand-categorized row (marked a transfer).

What changed: `markAsTransfers` takes `{ byHand }`. An automatic mark (the linker on a trade import, a manual entry and the pass after a sync, an import that turns a linked row into a cash transfer, an import's link through an alias, and an edit that makes a linked row a cash transfer under the linker's link) takes only the rows automatic pairing takes: never a row with `not_transfer`, never a hand-categorized row that is not a transfer. Such a row stays linked and as the household left it, and its investment row is the flow (A5(2)), so the account's value and return are the same and a rules run after the link finds nothing to reverse. The trade import's derived ledger rows keep a rule's "not a transfer" the same way. A link the household sets by hand (`PATCH /api/investments/transactions/:id` with `ledgerTransactionId`) is its word about that bank row, as pairing by hand is (decisions 52 and 106): it marks the row whatever a rule said (`not_transfer` cleared) and keeps a hand category on it, as before.

The plan now answers the question the reviewer left open: an automatic link must leave a `category_locked` row alone, as pairing does (decision 48). The reasons: A5's own rule is "exactly as pairing marks its legs"; the Phase 3 seams (P4) already make every other automation (the income feed) respect `category_locked`; and nothing is lost, since A5(2) counts the deposit in the account's value and return from the investment row, while the goal follows the household's categorization until the household marks the row a transfer (then the ledger row is the flow, counted once).

No repair migration. Migration 0005 marked hand-categorized rows too, as A5 first said, and such a mark cannot be told from one the household made: the row kept its category, and "not a transfer" on it puts it back in the plan. A row marked over a rule's "not a transfer" could only be written since migration 0009 added the column in this audit's a10 round; the next rules run returns it to the rule's choice, and with this fix nothing marks it again.
