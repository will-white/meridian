# Phase 2 build plan: Spending plan

Source of truth: the design spec linked from `CLAUDE.md`. Four area designs were produced by independent designers and merged by judges; they live in `docs/design/phase-2/` as records. Where this document and an area design disagree, **this document wins**: it reconciles the seams between areas. Where this document is silent, the area design applies (its algorithms, edge cases and hand-calculated test cases are the implementer's contract).

Scope (spec, Phase 2): buckets and categories, multi-month grid, rollovers, recurring detection, subscriptions page, cash-flow projection, dashboard. Gate: one full month budgeted in this app instead of the current one.

## Reconciled decisions (binding)

Conventions: money is `bigint` cents; `transaction.amount_cents` is signed (+ in, − out); every grid number is *bucket-natural* (positive is good): `bucketSign(income) = +1n`, else `−1n`; planned is a non-negative magnitude. Months are `YYYY-MM` strings; dates `YYYY-MM-DD`. One integer rule everywhere: **bigint division truncates toward zero** (pace, averages, monthly equivalents). Divisors are asserted `> 0n`.

1. **Rollover.** `category.rollover_mode` ∈ `none | surplus | all` (UI labels: None / Carry surplus only / Carry surplus and overspend) with `category.rollover_from_month` (the chain start; set to the current month when a carrying mode is first enabled, cleared on `none`). `month_plan.rollover_mode` is a nullable per-month override of the carry OUT of that month (the spec's column; the Phase 2 UI exposes only the category setting). Income categories are always `none` (API 400 `income_no_rollover`).
2. **Carried-in is computed on every read**, never cached: fold each category from `max(household_setting.plan_start_month, rollover_from_month)`. `month_plan.carried_in_override_cents` (nullable) is the spec's "carried-in amount": a pin for that month that feeds forward. `carryOut(none) = 0`, `carryOut(surplus) = max(0, remaining)`, `carryOut(all) = remaining`.
3. **month_plan rows** hold `planned_cents` (nullable, ≥ 0) + `planned_source ∈ manual | average | recurring | goal`, `rollover_mode` (nullable), `carried_in_override_cents` (nullable), `note`. A row is deleted when every nullable column is null. `planned_cents` null (or no row) = auto value: bills/income from active recurring occurrences, savings from the goal's monthly contribution, else 0 with source `none`. A nightly idempotent job `plan.close_month` freezes auto values (`recurring` / `goal`) into rows for completed months so history never shifts when a price changes; it never overwrites `manual`/`average` rows.
4. **Cell math** (plan-math area): `available = planned + carriedIn`; `remaining = available − actual`; `overspend = max(0, −remaining)` (0 for income); `committed = max(planned + carriedIn, actual) − max(carriedIn, 0)` (identical to `planned + min(carriedIn, 0) + overspend`; for income with carriedIn 0 it is `max(planned, actual)`). Both judges' formulas are this one.
5. **Summary per month**: `plannedLeftToSpendCents = planned(income) − planned(bills) − planned(savings) − planned(spending)` (the spec's literal formula); `leftToSpendCents = committed(income) − committed(bills) − committed(savings) − committed(spending)` (shown on the strip and dashboard, drives pace; equals the planned number when nothing happened); `toAssignCents = committed(income) − Σ planned(bills + savings + spending)` (zero-based presentation; no cross-month chain); `warning = displayed number < 0`; `pace` only for the current month: `daysLeft = daysInMonth − day + 1`, `perDayCents = left ≥ 0 ? left / daysLeft : 0`, `overCents = max(0, −left)`.
6. **Uncategorized and bucket_override.** No synthetic rows. Uncategorized non-transfer transactions sit in no bucket and do not move the numbers; the summary carries `uncategorized { count, cents }` per month and the dashboard review card counts them. `transaction.bucket_override` is not read by the Phase 2 grid (kept for a later phase).
7. **Goals.** One goal per savings-bucket category; the category row carries the goal. Goal actual for a month = categorized non-transfer rows (bucket-natural) **plus net transfer legs in the linked account** (inflows − outflows, `is_transfer = true`). Progress = `starting_cents + Σ actual over [start_month, current]`; `progressBp`, `remainingToTarget`, `monthsLeft`, `neededPerMonth = ceilDiv`, `projectedCompletionMonth`, `onTrack` per the grid-and-api design.
8. **Averages.** `GET /api/plan/averages?months=3|6|12&asOf=` returns every category's average: window `[asOf − n, asOf − 1]`, divisor = window months on/after the ledger's first transaction month (`monthsWithData`; 0 → all zero), truncate, clamp at 0. The client composes edits with `source: 'average'`. Fill right is also client-composed edits (`source: 'manual'`, the displayed value). `PUT /api/plan/cells` validates its optional re-read `range` (from ≤ to, at most 24 months, from 2000-01 on) before it writes anything, so a bad range never leaves a half-applied batch behind.
9. **Groups.** `category.group_id` nullable; ungrouped categories render after the bucket's groups; a category may only sit in a group of its own bucket (400); group bucket is immutable. Row order: bucket → groups by (position, name) with their categories by (position, name) → ungrouped categories.
10. **Settings.** One singleton table `household_setting` (id = 1): `plan_start_month`, `zero_based`, `low_balance_threshold_cents`, `primary_account_id`, `projection_default_days`, `timezone` (default `America/Denver`). `GET/PATCH /api/settings`.
11. **Audit.** `audit_log` (`batch_id` per request, `entity ∈ month_plan | category | category_group | savings_goal | recurring | rule | household_setting`, text `entity_id` (`${month}:${categoryId}` for cells), `action ∈ create | update | delete`, `before`/`after` JSON). Written by plan cell writes, category/group/goal/recurring/rule mutations and settings; never when before equals after. `GET /api/audit`.
12. **Recurring.** Table and engine per the recurring design: eight cadences (`weekly, biweekly, twice_monthly, monthly, bimonthly, quarterly, semiannual, yearly`), anchors (`anchor_day`, `anchor_day2`, `anchor_month`, `anchor_date`), signed `expected_cents`, `tolerance_cents`, `amount_mode`, `amount_locked`, `schedule_locked`, denormalised `next_due_date`, first/last charge, `charge_count`, `consecutive_missed`, `missed_from_date`, `confidence`, `source`, `status ∈ suggested | active | paused | cancelled | dismissed`, `status_reason`, `status_changed_at`, `detected_at`, `notes`; plus `account_id` (nullable; required to activate) and `transfer_account_id` (nullable; set → the item is a transfer). `transaction.recurring_id` links charges; series identity across runs is link overlap. `alert` table with typed columns and a unique `dedupe_key`; kinds `price_increase | new_recurring | missed_charge | trial_converted`.
13. **One schedule module.** `packages/shared/src/schedule.ts` (written in the skeleton) is the only occurrence generator: `occurrence`, `periodIndex`, `occurrencesInRange`, grace/tolerance tables. Auto-planned bills/income, the dashboard's bills-due list and the cash-flow engine all use it. Auto-planned occurrences for past months are bounded below by the item's `first_charge_date` (manual items: creation month).
14. **Cash flow.** Engine per the cash-flow design, with its recurring input shaped as `{ id, name, kind, accountId, transferAccountId, schedule, nextDueDate, amountCents }`: occurrences = `occurrencesInRange(schedule, nextDueDate, endDate + maxShift)`; an item whose `nextDueDate < today` posts once on today flagged overdue (the recurring refresh already advanced `next_due_date` past missed-with-grace occurrences). Card payments modeled with `account.payment_day`, `payment_from_account_id`, `statement_day`; per-account `low_balance_threshold_cents`. Spending remaining: current month = Σ over spending categories of `max(0, planned + carriedIn − actual)`; future months = Σ `(plan row ? planned : 3-month average)`, with a warning naming how many months fell back to averages. `POST /api/cashflow/projection`, no writes: it is marked `readOnly`, so the auth plugin lets the viewer role call it like a GET; an unknown or off-budget `accountIds` entry is 400 `bad_request` (the area design's code).
15. **Dashboard.** `GET /api/dashboard` per the grid-and-api `DashboardView`; bills due = active outflow items expanded with `occurrencesInRange(schedule, today, today + 14)` plus overdue items (`next_due_date < today`); net worth from `balance_snapshot` with `addMonthsClamped(today, −12)` and `newAccounts`; review counts: uncategorized, suggested recurring, open alerts. Computed per request, `Cache-Control: no-store`.
16. **`today`.** Clients send their local date; the API accepts it within ±2 days of the server date (else 400) and defaults to the server's date in the household timezone. Worker jobs compute today in the household timezone.
17. **Jobs.** `recurring.detect` (after every successful full sync, after CSV commit and manual transactions, on demand, and once per day after `DETECT_HOUR_UTC`) and `plan.close_month` (once per day, same tick). Both deduped. Moving `plan_start_month` earlier enqueues `plan.close_month` so the newly covered completed months freeze without waiting for the nightly tick.
18. **Monthly equivalents** on the Subscriptions page: `yearly = expected × {52, 26, 24, 12, 6, 4, 2, 1}`, `monthly = yearly / 12n` (truncate); totals from the yearly sum. The recurring design's TC9/TC16 expectations that used half-away-from-zero rounding are adjusted accordingly (430657; −4, +4, −149, −833, −2883, −10208, −999, −4333).

## Deviations from the spec's data-model table (flagged)

- Rollover mode lives on `category` (with a per-month override column on `month_plan`), and carried-in is a computed value with a nullable override column, not a stored amount.
- Added tables: `household_setting`, `audit_log`, `alert`; added columns on `account` (threshold, card payment), `transaction.recurring_id`.
- Added cadence `bimonthly` and recurring status `dismissed`.
- Planned source gains `goal`.
