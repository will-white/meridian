# Phase 2 build plan: Spending plan

Source of truth: the design spec linked from `CLAUDE.md`. Four area designs were produced by independent designers and merged by judges; they live in `docs/design/phase-2/` as records. Where this document and an area design disagree, **this document wins**: it reconciles the seams between areas. Where this document is silent, the area design applies (its algorithms, edge cases and hand-calculated test cases are the implementer's contract).

Scope (spec, Phase 2): buckets and categories, multi-month grid, rollovers, recurring detection, subscriptions page, cash-flow projection, dashboard. Gate: one full month budgeted in this app instead of the current one.

## Reconciled decisions (binding)

Conventions: money is `bigint` cents; `transaction.amount_cents` is signed (+ in, − out); every grid number is *bucket-natural* (positive is good): `bucketSign(income) = +1n`, else `−1n`; planned is a non-negative magnitude. Months are `YYYY-MM` strings; dates `YYYY-MM-DD`. One integer rule everywhere: **bigint division truncates toward zero** (pace, averages, monthly equivalents). Divisors are asserted `> 0n`.

1. **Rollover.** `category.rollover_mode` ∈ `none | surplus | all` (UI labels: None / Carry surplus only / Carry surplus and overspend) with `category.rollover_from_month` (the chain start; set to the current month when a carrying mode is first enabled, cleared on `none`). `month_plan.rollover_mode` is a nullable per-month override of the carry OUT of that month (the spec's column; the Phase 2 UI exposes only the category setting). Income categories are always `none` (API 400 `income_no_rollover`). A change of the category setting applies from the current month on: the months that already happened are pinned to the mode they ran under (audit decision A2 below).
2. **Carried-in is computed on every read**, never cached: fold each category from `max(household_setting.plan_start_month, rollover_from_month)`. `month_plan.carried_in_override_cents` (nullable) is the spec's "carried-in amount": a pin for that month that feeds forward. `carryOut(none) = 0`, `carryOut(surplus) = max(0, remaining)`, `carryOut(all) = remaining`. A month's stored `rollover_mode` and `carried_in_override_cents` always apply, also before the category's chain start; without a stored mode, months before the chain start behave as `none`, and the chain start itself begins at 0.
3. **month_plan rows** hold `planned_cents` (nullable, ≥ 0) + `planned_source ∈ manual | average | recurring | goal`, `rollover_mode` (nullable), `carried_in_override_cents` (nullable), `note`. A row is deleted when every nullable column is null. `planned_cents` null (or no row) = auto value: the occurrences of the category's confirmed recurring items (any bucket; decision 13 and audit decisions A1, A3), or the goal's monthly contribution where a goal plans the month, else 0 with source `none`. A nightly idempotent job `plan.close_month` freezes auto values (`recurring` / `goal`) into rows for completed months so history never shifts when a price changes or an item is paused, cancelled or resumed; it never overwrites `manual`/`average` rows, never freezes the current or a future month, and leaves a category's recurring value live while one of its active items still awaits an occurrence due in that month or earlier (audit decision A1).
4. **Cell math** (plan-math area): `available = planned + carriedIn`; `remaining = available − actual`; `overspend = max(0, −remaining)` (0 for income); `committed = max(planned + carriedIn, actual) − max(carriedIn, 0)` (identical to `planned + min(carriedIn, 0) + overspend`; for income with carriedIn 0 it is `max(planned, actual)`). Both judges' formulas are this one.
5. **Summary per month**: `plannedLeftToSpendCents = planned(income) − planned(bills) − planned(savings) − planned(spending)` (the spec's literal formula); `leftToSpendCents = committed(income) − committed(bills) − committed(savings) − committed(spending)` (shown on the strip and dashboard, drives pace; equals the planned number when nothing happened); `toAssignCents = committed(income) − Σ planned(bills + savings + spending)` (zero-based presentation; no cross-month chain); `warning = displayed number < 0`; `pace` only for the current month: `daysLeft = daysInMonth − day + 1`, `perDayCents = left ≥ 0 ? left / daysLeft : 0`, `overCents = max(0, −left)`.
6. **Uncategorized and bucket_override.** No synthetic rows. Uncategorized non-transfer transactions sit in no bucket and do not move the numbers; the summary carries `uncategorized { count, cents }` per month and the dashboard review card counts them. `transaction.bucket_override` is not read by the Phase 2 grid (kept for a later phase).
7. **Goals.** One goal per savings-bucket category; the category row carries the goal. Goal actual for a month = categorized non-transfer rows (bucket-natural) **plus net transfer legs in the linked account** (inflows − outflows, `is_transfer = true`). An account's transfers count toward exactly one goal: a second active goal on an account is refused (409 `account_linked`), and where several goals still link one account each month's legs go to one owner (audit decision A4). Progress = `starting_cents + Σ actual over [start_month, current]`; `progressBp`, `remainingToTarget`, `monthsLeft`, `neededPerMonth = ceilDiv`, `projectedCompletionMonth`, `onTrack` per the grid-and-api design.
8. **Averages.** `GET /api/plan/averages?months=3|6|12&asOf=` returns every category's average: window `[asOf − n, asOf − 1]`, divisor = window months the plan's ledger covers in full (`monthsWithData`; 0 → all zero): months after the month of the earliest on-budget transaction, plus that month when the transaction is dated the 1st (audit decision A6); truncate, clamp at 0. The client composes edits with `source: 'average'`. Fill right is also client-composed edits (`source: 'manual'`, the displayed value). `PUT /api/plan/cells` validates its optional re-read `range` (from ≤ to, at most 24 months, from 2000-01 on) before it writes anything, so a bad range never leaves a half-applied batch behind.
9. **Groups.** `category.group_id` nullable; ungrouped categories render after the bucket's groups; a category may only sit in a group of its own bucket (400); group bucket is immutable. Row order: bucket → groups by (position, name) with their categories by (position, name) → ungrouped categories.
10. **Settings.** One singleton table `household_setting` (id = 1): `plan_start_month`, `zero_based`, `low_balance_threshold_cents`, `primary_account_id`, `projection_default_days`, `timezone` (default `America/Denver`). `GET/PATCH /api/settings`.
11. **Audit.** `audit_log` (`batch_id` per request, `entity ∈ month_plan | category | category_group | savings_goal | recurring | rule | household_setting`, text `entity_id` (`${month}:${categoryId}` for cells), `action ∈ create | update | delete`, `before`/`after` JSON). Written by plan cell writes, category/group/goal/recurring/rule mutations and settings; never when before equals after. `GET /api/audit` (filters `entity`, `entities`, `entityId`, `batchId`); the Plan page's History panel reviews and undoes the plan's batches (audit decision A29).
12. **Recurring.** Table and engine per the recurring design: eight cadences (`weekly, biweekly, twice_monthly, monthly, bimonthly, quarterly, semiannual, yearly`), anchors (`anchor_day`, `anchor_day2`, `anchor_month`, `anchor_date`), signed `expected_cents`, `tolerance_cents`, `amount_mode`, `amount_locked`, `schedule_locked`, denormalised `next_due_date`, first/last charge, `charge_count`, `consecutive_missed`, `missed_from_date`, `confidence`, `source`, `status ∈ suggested | active | paused | cancelled | dismissed`, `status_reason`, `status_changed_at`, `detected_at`, `notes`; plus `account_id` (nullable; required to activate and kept while active: 400 `account_required`, audit decision A12) and `transfer_account_id` (nullable; set → the item is a transfer). `transaction.recurring_id` links charges; series identity across runs is link overlap. `alert` table with typed columns and a unique `dedupe_key`; kinds `price_increase | new_recurring | missed_charge | trial_converted`.
13. **One schedule module.** `packages/shared/src/schedule.ts` (written in the skeleton) is the only occurrence generator: `occurrence`, `periodIndex`, `occurrencesInRange`, grace/tolerance tables. Auto-planned recurring items, the dashboard's bills-due list and the cash-flow engine all use it. Auto-planned occurrences follow what happened (`recurringPlanCounts` in `packages/shared/src/recurringPlan.ts`, audit decision A1): a linked charge is one occurrence planned in the month the charge posted (for active, paused and cancelled items); only an active item is planned ahead, from the day it began to be expected (`missed_from_date`: confirm, resume or manual create), for the occurrences no charge is linked to; a completed month keeps only what was paid in it, and an overdue occurrence that is still awaited is held in the current month.
14. **Cash flow.** Engine per the cash-flow design, with its recurring input shaped as `{ id, name, kind, accountId, transferAccountId, schedule, nextDueDate, amountCents }`: occurrences = `occurrencesInRange(schedule, nextDueDate, endDate + maxShift)`; an item whose `nextDueDate < today` posts once on today flagged overdue (the recurring refresh already advanced `next_due_date` past missed-with-grace occurrences). Card payments modeled with `account.payment_day`, `payment_from_account_id`, `statement_day` (a payment pays what is still unpaid of the statement, audit decision A7); per-account `low_balance_threshold_cents`. Every active item with an account is a dated event, whatever its category's bucket. Spending remaining: current month = Σ over spending categories of `max(0, planned + carriedIn − actual)`; future months = Σ `(plan row ? planned : 3-month average)`, each category less the dated charges of its own recurring items that post in that month (never below 0, audit decision A3), with a warning naming how many months fell back to averages (or saying that no complete month of history exists yet). Planned income, bills and savings that no recurring item dates are not forecast and are named (audit decision A14). `POST /api/cashflow/projection`, no writes: it is marked `readOnly`, so the auth plugin lets the viewer role call it like a GET; an unknown or off-budget `accountIds` entry is 400 `bad_request` (the area design's code).
15. **Dashboard.** `GET /api/dashboard` per the grid-and-api `DashboardView`; bills due = active outflow items expanded with `occurrencesInRange(schedule, today, today + 14)` plus overdue items (`next_due_date < today`); net worth from `balance_snapshot` with `addMonthsClamped(today, −12)` and `newAccounts`; review counts: uncategorized, suggested recurring, open alerts. Computed per request, `Cache-Control: no-store`.
16. **`today`.** Clients send their local date; the API accepts it within ±2 days of the server date (else 400) and defaults to the server's date in the household timezone. Worker jobs compute today in the household timezone.
17. **Jobs.** `recurring.detect` (after every successful full sync, after CSV commit and manual transactions, on demand, and once per day after `DETECT_HOUR_UTC`) and `plan.close_month` (once per day, same tick). Both deduped. Moving `plan_start_month` earlier enqueues `plan.close_month` so the newly covered completed months freeze without waiting for the nightly tick.
18. **Monthly equivalents** on the Subscriptions page (recurring outflows that are not transfers, audit decision A13): `yearly = expected × {52, 26, 24, 12, 6, 4, 2, 1}`, `monthly = yearly / 12n` (truncate); totals from the yearly sum. The recurring design's TC9/TC16 expectations that used half-away-from-zero rounding are adjusted accordingly (430657; −4, +4, −149, −833, −2883, −10208, −999, −4333).

## Decisions made during the audit

These were taken while fixing the Phase 1–3 audit findings. They are binding like the reconciled decisions above and, where they differ from an area design in `docs/design/phase-2/`, they win.

1. **A goal has no projected completion month past 2199-12.** `goalProgress` returns `projectedCompletionMonth: null` when the monthly contribution would not reach the target by December 2199 (the last month a caller may name), instead of a month with a five-digit year that no contract can carry: before, a goal of $100,000 at $1 a month answered 500 on the Goals and Plan pages. The Goals page says "not reached before 2200 at this pace".

Plan math (findings p2-01, p2-04, p2-05, p2-06, p2-09, p2-12, p2-13, web-07, live-14):

- **A1. Auto-planned recurring values follow what happened, not the calendar** (findings p2-01, p2-05, p2-13). A linked charge is one planned occurrence in the month the charge posted: a salary due on the 1st that arrives the Friday before belongs to the earlier month, a bill due on the 30th that posts on the 2nd to the later one. Only an active item is planned ahead, and only from the day it began to be expected (`missed_from_date`), so pausing or cancelling keeps what was already paid and resuming never back-fills the months on hold. A completed month keeps only what was paid in it: an expected paycheck or bill that never arrived does not stay in a closed month's left to spend. An occurrence from last month that is still awaited (overdue, inside the cadence's grace) is planned in the current month, the same rule the cash-flow projection uses; once the refresh writes it off as missed it is planned nowhere. A missed occurrence inside the current month stays planned until the month ends (the bill may still come). `plan.close_month` freezes completed months only and waits for a category while one of its active items still awaits an occurrence from that month, so a charge that syncs a day late is frozen with its month. This replaces the old rule "every schedule occurrence in its nominal month, bounded below by `first_charge_date` / the creation month".
- **A2. A rollover change is never retroactive** (p2-04). When a category's mode or start month changes, the months from the old chain start up to the month before the current one (or before a later new start month) are pinned to the old mode in `month_plan.rollover_mode`, in the same audit batch. The engine honours those pins whatever the category setting becomes later, so closed months keep their carried-in, committed and left-to-spend figures, and the current month keeps what it was handed. Keeping the start month and changing the mode preserves the balance; choosing a later start month restarts the envelope at zero there (and still leaves earlier months alone); choosing an EARLIER start month is an explicit request to recompute history and pins nothing.
- **A3. A confirmed recurring item is planned in its own category, whatever the bucket** (p2-06). The spec's "confirmed items feed the bills bucket" is met by categories in that bucket; a gym membership the owner files under Health (spending) is planned there rather than silently dropped. Amounts are netted in the bucket's direction (a recurring refund lowers a spending category's plan; a net that is not positive plans nothing). In a savings category the goal's monthly contribution takes precedence for the months it plans. In the cash flow every active item with an account is a dated event, and a spending category's dated charges are taken out of that category's share of the spending spread, so a charge is never both an event and part of the spread and skipping it in a what-if removes it altogether. A typed amount still replaces the automatic value for its month.
- **A4. One active goal per linked account** (web-07). A transfer must count once. Sharing an account between goals would need a per-transfer allocation the spec does not describe, and a computed split (for example by monthly contribution) would move every goal's past progress whenever a contribution changed. So linking an account that already feeds an active goal is refused with 409 `account_linked`, naming that goal, and the form shows which accounts are taken. A completed or archived goal may keep its link: among several goals on one account, each month's transfers go to one owner (an active goal first, then the latest start month once started, then the oldest goal), which also keeps data from before the rule from double counting. The drill-down behind a goal lists the transfer legs only for the months the goal owns.
- **A5. Split transactions are a first-class edit** (p2-09). `PUT /api/transactions/:id/splits` replaces a transaction's lines: two or more lines that add up to its amount exactly, each with a category and a non-zero amount (a line may run the other way, such as cash back); an empty list removes the split. The row's own category is cleared and locked while it is split; picking one category for the row removes the split. A split row counts in each line's category everywhere: the grid, the drill-down, the register's category filter, and it is never "uncategorized" (plan badge, dashboard review count, uncategorized filter). The register has a split editor on every non-transfer row.
- **A6. Plan scope for drill-downs, and averages over complete months only** (p2-12, live-14). The list behind a plan cell is requested with `planScope=true`: on-budget accounts plus the investment income feed, the same predicate the cell's actual uses, so the list adds up to the number clicked. Averages divide by the months the on-budget ledger covers from their first day: the month of the earliest on-budget transaction counts only when that transaction is dated the 1st, because a first sync reaches back a fixed number of days and its first month is partial. With no complete month in the window the averages are zero, "plan from average" writes nothing and says so, and the cash-flow projection warns that unplanned spending categories are projected at 0.

Recurring detection, subscriptions, alerts and cash flow (findings b5-recurring-cashflow-01 to -14; record in `docs/audit/phases-1-3/b5-recurring-cashflow.md`):

- **A7. A card payment pays what is still unpaid of the statement** (b5-01). Payments and credits posted to the card after the statement close are already in today's balances, so paying the whole close balance again on the payment day double counts them. With `statement_day` set and the close before today, the loader passes `knownStatementBalanceCents` = the balance at the close plus every positive card row (payment, refund; posted or pending) dated after the close through today, which is the opening balance less the card's charges since the close (`cardUnpaidStatementBalance`); the engine pays `max(0, −that)`. A statement paid in full before the payment day is not paid again, a partial payment leaves the rest, and an autopay that posted today is not paid a second time on day 0. Later payments read the projected balance at their close, as before.
- **A8. A price change is the expected amount from its first charge** (b5-02). The recurring design's resolutions plan the new price "immediately rather than two charges later", and the spec alerts on a price increase "versus the last charge". `classifyAmounts` is therefore fixed (expected = the last charge, tolerance max($1, 1%)) when the last three charges agree, or when the newest one or two agree with each other and the three before them agreed (a level shift: a price increase or a cheaper plan). Any other spread stays variable. The design's corrected TC8 (variable at the old price until two, in fact three, charges at the new one) is replaced: after 15.49 × 5 and one 17.99 the item is fixed at 17.99 ± 1.00, plans and projects 17.99, and a further increase alerts again. A detection's amounts (mode, expected, tolerance) are classified over its on-cycle charges, the ones it links, so an extra or a missed charge never sets the expected amount and the refresh after a confirm reproduces it; the ×2 dispersion and minimum-charge gates still look at the whole group.
- **A9. A seasonal bill is one variable series** (b5-07). The spec's example of a variable bill is a utility, and a heating bill's winter peak is often more than twice its median. When the whole group, the per-account split and the amount clusters yield fewer than two series, a group whose amounts are dispersed is accepted as one variable series if it has at least six charges (`MIN_CHARGES_DISPERSED`) and every charge is on-cycle on the chosen cadence (no extra, no miss): one bill whose amount moves with the season, not two series mixed (two clusters that are each a series, such as iCloud and Music, still win). The matcher's amount gate for a variable item spans ⅓ of the smallest to 3 × the largest of the expected amount and the last six linked charges, so the winter charges keep matching after a summer confirm; fixed items keep ½× to 2× the expected amount. The expected amount stays the upper median of the last six charges (a known limit for seasonal bills).
- **A10. The detector refreshes only what the owner has not taken over** (b5-04). Rewriting a mapped suggestion keeps a locked amount (expected, tolerance, mode) and a locked schedule (cadence and anchors; next due follows the locked schedule), fills the category only when the row has none, and moves the account only when the detection's last charge is a new one. The rewrite is conditional on the row still being a suggestion (`... where status = 'suggested' returning`): a confirm or dismiss that raced the run wins, and the row only gets `detected_at`.
- **A11. A cancelled item does not absorb a resubscription** (b5-05). A cancelled row keeps its links, so the series still maps to it. The charges dated after its cancel (`status_changed_at`) that it does not hold are detected on their own; a series among them is suggested anew (mapped by overlap to the suggestion of an earlier run, so it is not duplicated), with a `new_recurring` alert when it is new under B9. Dismissed rows stay sticky as designed.
- **A12. An account the owner picks stands** (b5-08, b5-09). The refresh moves `account_id` to the account of the last charge only when that charge was just linked (a matcher run, a manual link, a move), so a card move is still followed when its first charge arrives, but an edit is not undone by the next refresh. An item becomes or stays active only with an account (400 `account_required` on a confirm, a resume, a reactivation, a manual create and an edit that would clear it); a paused or cancelled item may lose it and needs one to resume.
- **A13. The Subscriptions page lists spending only** (b5-06). An item with `transfer_account_id` moves money between the household's own accounts (decision 12) and is neither listed nor counted on the Subscriptions page; it stays on the Recurring page and in the cash flow. The page's "auto-paused" badge reads `statusReason = 'missed_3'` (b5-10), which outlives `consecutiveMissed`. `price_increase` is raised for outflows only (b5-13): a raise on a paycheck is not a price increase.
- **A14. Planned amounts without a schedule are named, not forecast** (b5-03). A value typed into the grid for an income, bills or savings category, or a goal contribution, has no date, so the projection does not post it (posting it at a guessed date, or spreading it, would double count the recurring auto-fill whenever both exist). A month planned automatically from recurring items is their schedule and is not listed (an occurrence missed in the current month stays planned until the month ends but is not projected; its missed-charge alert reports it). Instead the loader compares each such category's plan per month (the current month: planned less actual, never below 0; later months: planned) with the bucket-natural amount of its own dated recurring occurrences in that month (overdue ones post today; the horizon's last month counts in full) and returns the positive rest as `unscheduled` (month, category, bucket, amount), plus one warning naming the categories. The Cash flow page lists them with a link to the Recurring page's add form, prefilled with the category and direction.
- **A15. A linked charge can be moved to another item** (b5-12). `POST /api/recurring/:id/link` takes `move: true`: after the usual checks (same payee and direction, not a transfer, a free period), a charge held by another item leaves it (that item is refreshed) and joins this one in the same transaction. Without `move` a charge linked elsewhere is still 409 `conflict`. The Charges panel offers only what the route accepts: charges of the item's payee and direction, "link" for a free one and "move here" for one held by another item.

Accounts, net worth and the cash flow (findings a6-text-rules-accounts-07 and -08; record in `docs/audit/phases-1-3/a6-text-rules-accounts.md`):

- **A16. Closing an account hides it from now on; it does not rewrite the past** (a6-07). The dashboard's net worth sums today's latest balances of the open accounts and the year-ago balances of every account, closed ones included, so closing an emptied savings account no longer turns its old balance into a twelve-month gain that never happened. The grid-and-api design's "closed accounts excluded" now applies to today's figure only.
- **A17. The projection is cash: assets and loans start off budget** (a6-08). The spec's projection starts from "today's balance" of the accounts the household spends from; a house or a car loan on budget added its value to the combined line, the 30-day dashboard line and its low point. Phase 1 audit decision 65 makes asset and loan accounts start off budget (beside the investment types of Phase 3 decision 15); the Budget column still switches any account on or off.

Spending plan, goals and dashboard in the web app (findings b7-plan-ui-01 to -13; record in `docs/audit/phases-1-3/b7-plan-ui.md`):

- **A18. Fill right copies the value being committed** (b7-01). The keyboard's fill right (Ctrl/Cmd+Shift+→) sends the cell's own edit and one edit per later visible month in one request (one audit batch), all with the amount just typed; with nothing typed it copies the value the cell shows (the resolved value, the grid design's rule). Emptying a typed cell and pressing the shortcut sends only the clear: the automatic value the cell falls back to is known once the server answers, and the cell menu's Fill right copies it from there. Before, the shortcut committed the typed amount and then copied the value from before the edit, writing it as manual overrides that hid recurring and goal values.
- **A19. Grid rows are as tall as their content; subtotals and the strip are labelled like the cells** (b7-02, b7-03, b7-11). Row heights are measured (the old fixed heights are the minimum), so wrapped amounts and the "+$ in" and "incl. $ pending" notes are never drawn under the next row. A bucket or group subtotal stacks like a category cell: planned, then actual and the remaining with its label ("left", "to come", "extra"). The summary strip names each committed bucket total on its own line in every month cell, in compact mode too (the spec puts the bucket totals in the strip, which compact mode does not compact). Compact mode shows the remaining only, as the spec says; the planned input lies over it and appears, whole, while it has focus, so typing and keyboard movement work as before.
- **A20. The drill-down is a panel on the Plan page** (b7-04). Clicking an actual, the cell menu's "Show transactions" or a month's uncategorized badge lists the cell's transactions (the register's plan-scope query) under the grid, which shrinks so both stay in view. A row is dragged onto any category row of the grid, or moved with its category select (the keyboard's way); a transfer leg and a split row are not movable there (a split is changed line by line in the register's split editor; the register follows the same rule). The move is the register's `PATCH /api/transactions/:id`, followed by the register's "always do this" prompt when the row has a payee. "Open in the register" keeps the old page link.
- **A21. The plan carries its start month** (b7-05). `PlanResponse.startMonth` is `household_setting.plan_start_month`. Months before it take no plan edits (the API's 400 `before_plan_start` is unchanged), so the grid shows their planned values read-only with the reason in the cell's tooltip, the strip marks those months "before the plan start" with a link to Settings, and the cell menu offers only the rollover setting and the transactions there. A fresh install still starts the plan in its first month.
- **A22. Pages follow the local date** (b7-07). The Dashboard and Plan pages re-read the browser's local date at local midnight and when the page becomes visible or gains focus (`useLocalToday`), so a page left open overnight asks for the new day (decision 16) instead of yesterday, and is never refused for a date more than two days old.
- **A23. Categories are managed where they are planned** (b7-08, b7-09). The category manager changes a category's bucket (the grid design's "bucket stays directly editable on PATCH /categories", with a confirmation that its past months move too; a goal's category can only stay in savings) and deletes an unused one (a category still referenced answers 409 with the server's "hide it instead" reason). The goal form keeps the goal's own category selectable when it is hidden, marked "(hidden)", so a goal on a hidden category stays editable.
- **A24. A viewer sees the plan and the goals read-only** (b7-10). Phase 2 and Phase 3 conformance (audit batch b9-conformance-plan-investments, findings 02, 03, 04 and 07; record in `docs/audit/phases-1-3/b9-conformance-plan-investments.md`):

- **A28. The cash flow starts each account from what is known of it today, and says so** (b9-02). The spec's projection starts from "today's balance". A feed account's opening is still the bank's balance plus pending rows, passed through when it is old (the cash-flow design). An account without a bank feed has only the balance typed on the Accounts page (Phase 1 decision 63), and a bank CSV never changes it, so its opening is that balance plus every posted row dated after the balance's date through today (a balance is the end of its day; pending rows as before); `CashFlowAccount` and the response carry `rolledForwardCents`, `rolledForwardRows` and `dataThrough` (the last day the opening covers). An opening whose `dataThrough` is more than two days before today (`STALE_OPENING_DAYS`) is named in the warnings: "Savings: the projection starts from the balance of 09/15/26; record a newer balance or import its transactions", or for a feed account "…from the bank's balance of 11/10/26; sync its connection for a newer one". The Cash flow page lists each account's opening with its date ("balance of 10/31/26 + 2 transactions through 11/06/26 (−$950.00)"), marked when stale, and the dashboard's 30-day card says "Starts from balances as of …" with the oldest `dataThrough` (`DashboardView.cashFlow.balancesAsOf`). The Accounts page and net worth still show the typed balance: rolling it forward there would invent a balance the household never recorded. Chosen over a warning alone (the auditor's second option) because a low point that ignores every row imported since the last typed balance is wrong, not just old.
- **A29. The plan's history can be reviewed and undone on the Plan page** (b9-03). The spec keeps history of plan edits "so changes can be reviewed and reverted"; only rules had a page for it. **History** on the Plan page (and **History of this cell** in a cell's menu) lists the audit entries of plan cells, categories, groups, goals, recurring items and settings, newest first, grouped by the request that wrote them (one batch: a fill-right, a plan from average, an edit), with who and when, each in words ("Dining · Nov 2026: planned $250.00 (was automatic)", "Goal Emergency fund: monthly contribution $500.00 → $400.00"). `GET /api/audit` gains `entities` (a comma-separated list) so the panel is one keyset-paginated list. An owner's **Undo** follows the grid-and-api design (revert is client-side): `batchUndo` (`packages/shared/src/planHistory.ts`) reads every entry of the batch and sends each updated goal, setting, category, group or recurring item back to its `before` through its own PATCH (newest change first), then one `PUT /plan/cells` with every cell's `before` (a cell the batch created is cleared, so the automatic value shows through). The undo is a new batch, so it can itself be undone. A cell's own history lists that cell's changes, and its Undo puts back that cell only. A batch that created or deleted a category, group, goal or recurring item, changed an order, or confirmed a suggestion is not undoable from the history as a whole (the panel says why; those are put back on their own pages), so an undo never leaves half a change behind; a value frozen from a recurring item or goal in a completed month comes back with its amount as a typed value (the only source the route takes). When later changes touched the same values the owner is asked first. A viewer sees the history without Undo.
- **A30. The month window moves and shrinks as well as grows** (b9-07). The spec's columns are "adjustable". **‹ Earlier** and **Later ›** move the window one month and keep its size (they used to widen it and were disabled at 24 months, so months more than 22 before the current one could not be reached), and a **Months shown** select picks 1 to 24 columns: the current month stays in view at the same relative place (6 is the default's last 2, current, next 3; 1 is the current month alone). The window stays inside 2000-01 to 2199-12, the months the API serves.
