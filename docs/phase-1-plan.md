Source of truth: the design spec (linked from `CLAUDE.md`). This plan says what Phase 1 builds, where it lives, and where it deliberately departs from the letter of the spec or `CLAUDE.md`.

## Package responsibilities

- `packages/shared` is isomorphic (runs in browser and Node). It holds Zod contracts for every API route, the SimpleFIN v2 response schema, and the pure engines: `normalizePayee`, `evaluateRules`, `pairTransfers`, `matchPendingToPosted`, CSV parse + map, `sanitizeText`, and AES-256-GCM helpers on Web Crypto. Every engine has hand-calculated Vitest cases.
- `packages/db` holds the Drizzle schema, migrations, a programmatic migrate runner, and the data services that apply the engines to rows: `upsertTransactions` (dedupe by account + external id, pending replacement), `applyRules`, `pairTransfersForAccounts`, `importCsv`, `jobs`. Integration tests run against `TEST_DATABASE_URL` and skip when it is unset.
- `apps/worker` is the only process that talks to the outside world (spec: "the worker is the only container that talks to the outside world"). It runs the SimpleFIN client, a Postgres-backed job runner (`FOR UPDATE SKIP LOCKED`), and the 6-hour scheduler.
- `apps/api` validates with Zod, owns sessions, and enqueues jobs for anything that touches SimpleFIN. It serves the built UI in production.
- `apps/web` is React + Vite + TanStack Query + React Router, plain CSS, PWA manifest already configured.

## Data model (Phase 1)

Tables from the spec: `connection`, `import_log`, `account`, `balance_snapshot`, `transaction`, `split`, `payee`, `rule`, `tag`, `transaction_tag`, plus `user`, `session` and `sign_in_event` for auth.

Additions beyond the list, each with a reason:

- `job`: `CLAUDE.md` fixes "jobs are queued in Postgres" and the spec routes all SimpleFIN traffic through the worker, so claim and sync run as jobs.
- `category` (minimal: name, bucket, hidden): the Phase 1 UI must categorize and the rules engine must set a category, so a target table is needed. `category_group` and `month_plan` stay in Phase 2.
- `connection.claim_token_enc` and `connection.last_errors` (jsonb): the pasted token waits encrypted for the worker to claim it; `errlist` entries surface per connection.
- `connection.synced_through`: the high-water mark that the next sync overlaps by 7 days. It is the day through which every account is complete, so it moves only after a complete response (audit decision 24).
- `connection.last_attempt_at` and `connection.sync_paused` (migration 0006): when a sync last ran to its end, whether it worked or not, and whether the Bridge refused the connection outright. The scheduler spaces syncs from the first and skips connections with the second (audit decision 27).
- `account.balance_cents`, `available_cents`, `balance_date`: current balance for the accounts list, with history in `balance_snapshot`.
- `transaction.is_transfer`, `source`, `import_log_id`, `posted_at`, `memo`: rule action "mark transfer", provenance, and the SimpleFIN fields.
- `transaction.category_locked`: set when the user categorizes by hand, so re-running rules never overwrites a manual choice.
- `transaction_alias` and `transfer_dismissal` (migration 0007): external ids the ledger knows under another row of the account (a CSV row the feed has, the old id of a row the feed took over, a pending copy of a posted row) or that the household deleted, and pairs the household undid (audit decisions 42, 47, 48 and 50).
- `transaction.not_transfer` (migration 0009): a rule said the row is not a transfer, so automatic pairing leaves it alone (audit decision 106). The same migration makes `import_log.connection_id` `ON DELETE SET NULL`: removing a connection or a CSV profile keeps its import logs (audit decision 107).
- `passkey` and `webauthn_challenge` (migration 0010): a member's passkeys and the WebAuthn challenges waiting for an answer (audit decision 112).
- `user.last_sign_in_at` (migration 0011): the time of the member's last completed sign-in (password and code, or a passkey), written with its sign-in event. It was read from the sign-in activity, which is deleted after 90 days, so "Last sign-in" turned into "never"; the migration fills it from the activity there is (audit decision 13).

## Sync pipeline (per connection, in the worker)

1. Window: `start-date` = `synced_through − 7 days`, or `now − 93 days` on first sync and on a full resync, and never further back than `now − 93 days`. Always `pending=1`. `balances-only=1` is used by the "refresh balances" job.
2. Raw response goes to `import_log` first, before any parsing, whatever its shape: a body that is not JSON is kept as `{ "notJson": … }`, and NUL characters and unpaired surrogates, which `jsonb` refuses, become U+FFFD, and nesting deeper than 1000 levels, which could not be written, becomes a marker (audit decision 123). The stored copy is then read one account and one transaction at a time, so an entry that cannot be read is skipped and reported, never the whole response; `errors` or `errlist` sent as a single value is read as a list of one, and only a body without a list of accounts fails (audit decisions 31, 32 and 122).
3. Accounts upsert by (connection, external id); balance snapshot written per account per balance date. Amounts and balances are protocol numeric strings, read to the cent (a sign, any number of decimals, an exponent); one that cannot be read costs only that transaction or that balance (audit decision 30).
4. Transactions: upsert by (account, external id). Bank-owned fields (amount, date, description, pending) update; user fields (category, payee if locked, notes, tags) never do. The date is `transacted_at`, else `posted`, else the household's day (audit decision 33); a stored row keeps its date while the item carries neither, so an undated hold keeps the day it was first seen (audit decision 108). An amount that changes under the same id releases the row's transfer pair (audit decision 109). An account the household closed gets no transactions (audit decision 34). An id kept in `transaction_alias` is a duplicate and is left alone; an item that is the same purchase as a CSV or manual row takes that row over instead of being inserted, and so does an item of an account whose ids the feed re-keyed (audit decisions 42 and 43).
5. Pending → posted: a posted item whose id is new is matched to a local pending row in the same account, any pending row the feed no longer lists whatever its date, then one it still lists next to its posted form: by amount (equal, or changed by a tip or a settled hold), date within 5 days and description (they must share something; best similarity first). That row is updated in place (new external id, `pending=false`), keeping its id and user edits. Pending rows that are neither returned nor matched are deleted, whatever their date, after their transfer partners are released (audit decisions 44 to 47 and 49).
6. New rows: normalize payee → run rules (against the payee the name resolves to, aliases included, audit decision 54) → pair transfers across all of the user's accounts within 3 days. An ingest, from the feed or from a file, and the pairing pass each take the ledger lock first, so a CSV commit and a sync of the same days run one after the other (audit decision 104).
7. `errlist` entries are stored on the connection; `con.auth` sets status `auth_required`; HTTP 403 on sync sets `auth_required`; 402 sets `error` with a "subscription" message; 403 on claim sets `error` with the "token may be compromised" message. All server text is sanitized before it is stored for display. A sync that fails empties the stored entries (they described the response before it), except `sync.gap` notices, which stay until the household dismisses them (audit decision 116), and a network failure says why the server could not be reached.
8. A response that carries a connection (`con.*`) or account (`act.*`) problem is applied, but not trusted to be complete: the pending rows of the accounts it covers are kept, and the high-water mark does not move (audit decisions 24 and 26). A balances-only refresh never moves the mark, but one that finds an account (new, or attached again) clears it, so the next full sync asks for that account's history (audit decision 115).
9. Scheduling: a connection is due 6 hours after its last attempt, successful or not. After a failed attempt the next one gets a single try instead of the queue's three; after a 403 or 402 nothing is scheduled until a sync started by hand succeeds (audit decision 27).

## Rules engine semantics

Rules run in `position` order. Every rule whose conditions all hold applies its actions; a later rule overrides an earlier one for the same field, tags accumulate, and a rule may set `stop` to end evaluation. Conditions: payee (equals, contains, starts with, regex), description (same operators), signed amount range in cents, account, day of month. Actions: set payee, set category, add tags, mark as a transfer or as not a transfer; "not a transfer" holds over automatic pairing and, run on a paired row, undoes the pair (audit decision 106). A payee condition also holds on the names merged into the payee; text compares case-insensitively with Latin accents folded; patterns run on RE2 (linear time); a day range may wrap past the month end (audit decisions 55 to 59).

## Transfer pairing

Candidates are unpaired transactions in the user's own accounts, except rows the household categorized by hand that are not marked as transfers, and rows a rule said are not transfers (audit decision 106). An outflow pairs with the inflow of exactly opposite amount in a different account whose date is within 3 days, choosing the closest date (earliest on a tie), and the pass finds as many pairs as the legs allow (audit decision 51). Each transaction pairs at most once, and two rows the household unpaired never pair with each other again (audit decision 48). Both legs get the same `transfer_pair_id`, `is_transfer=true`, and their category is cleared so they leave the budget. A pair id always names two rows: a leg that is removed releases its partner (audit decision 49), and a leg whose amount the bank changes, or that a rule says is not a transfer, releases the pair (audit decisions 106 and 109). The register also pairs two rows by hand and marks a row as a transfer without its other leg (audit decision 52).

## CSV import

Mapping per institution is stored on a `connection` of type `csv` (`csv_mapping`). The mapper supports header or index columns, several date formats, a single signed amount column (with optional inversion) or separate debit and credit columns, and optional memo and id columns. Rows without a bank id get a stable external id: `csv2:` + SHA-256 of date, amount and the description as the file has it (white space collapsed, lower case; no payee heuristics), with an ordinal for identical rows in the same file (audit decision 105; rows imported before it keep their `csv:` ids). Re-importing the same or an overlapping file creates no duplicates, also with another id column or after an update, and neither does a file over days the feed or the household already has: a row that is the same purchase as one of theirs is not inserted, and its id is kept so a re-import knows it (audit decisions 42 and 105). An amount with a decimal comma ("12,50") is refused, not read as thousands (audit decision 111). An import can be undone (audit decision 50).

The Import page previews the file before anything is written: one preview per change of the file, account, saved profile or mapping (audit decision 29), the rows the ledger already has marked as duplicates, and the commit enabled only for the preview that is on screen. Its mapping editor offers the columns by header name, or by position for a file without a header row (audit decision 121).

## Auth

First run creates the owner (`POST /api/auth/setup`; of any number of setup requests that arrive together, exactly one creates an account). Passwords hash with Argon2id (19 MiB, 2 iterations, parallelism 1). TOTP enrollment is required before the app opens; the secret is stored encrypted with `SECRETS_KEY`, and a code is accepted once (the last accepted 30-second step is kept per user). Login routes are rate-limited, per client address and per account (see the audit decisions at the end of this file).

Passkeys (spec: "optional passkeys"): a signed-in member adds passkeys under Settings, re-entering the password; a passkey then signs that member in on its own, the device's screen lock standing for the password and the code (user verification required). The password and the authenticator stay; clearing a member's second factor removes their passkeys too (audit decision 112).

Sessions: the cookie (signed, HttpOnly, SameSite=Lax, `Secure` in production) carries a random 256-bit id; the `session` table stores only its SHA-256. A password alone gets a ten-minute session that reaches nothing but the two-factor routes and is deleted at the fifth wrong code. When the code is accepted a new id is issued (the password-only row is never promoted) that lasts `SESSION_TTL_DAYS` (30) or `SESSION_IDLE_DAYS` (14) without a request, whichever ends first. The worker deletes expired rows hourly.

Roles (spec: owner and viewer): the owner adds viewers under Settings (`/api/users`, owner only), sets a new password for one who forgot theirs, clears the second factor of one who lost their phone, and removes them. A viewer reads everything and changes nothing except their own sign-in. Every member changes their own password, replaces their authenticator and reviews or ends their sessions under Settings (`/api/auth/password`, `/api/auth/totp/replace`, `/api/auth/sessions`); the sign-in activity (`/api/auth/activity`) shows completed sign-ins and failed attempts. A locked-out owner recovers from the server's console with `apps/api/dist/admin.js` (README, "Locked out"). Member changes are in the audit log (entity `user`), never with a hash or a secret.

The guard runs in Fastify's `onRequest` hook, before a body is read: every route is closed unless its `config.auth` opens it (`static` for the files of the web app, `public` for health and the sign-in routes, `session` for the two-factor routes; the default `full` needs a verified session, and a change also needs the owner role). In production the API serves the built web app from `WEB_DIST_DIR`; those files and the SPA fallback are `static`: no session, no database query, so the setup and sign-in screens load in a fresh browser.

## Deviations and open points

- `packages/db/src/services` holds the persistence side of the ledger pipeline rather than a sixth package, to keep the five-workspace layout in `CLAUDE.md`.
- `category` is pulled forward from Phase 2 in minimal form (reason above).
- SimpleFIN hosts were unreachable from the build container, so the client follows protocol v2 as described in `CLAUDE.md` and the public spec from memory. Schemas are lenient (`passthrough`), the response is read one entry at a time and raw payloads are logged, so a field mismatch is recoverable without a resync (audit decisions 31 and 32).
- The spec's "requests only accounts that need transactions" is met in what is ingested, not in the request: a full sync asks for every account, so that one added at the Bridge is found, and an account the household closed gets no transactions (audit decision 34).
- The Phase 1 gate's "3 months of real transactions" is exercised with a deterministic 3-month fixture through two overlapping syncs and a repeat sync. Running it against a real Bridge token is the user's acceptance step.

## Decisions made during the audit

Serving and guarding the API (audit batch "serve and guard"):

1. **The web app's files are public; only `/api` is guarded.** `@fastify/static` is registered in its own scope whose routes are marked `auth: "static"`; the guard's default for every other route stays `full`. Static routes and unknown paths never read the session or the database. (Which unknown paths get the shell: decision 113.)
2. **Authentication runs before the body is read.** The guard moved from `preHandler` to `onRequest`: an anonymous caller gets 401 (403 `setup_required` before the owner exists) and a viewer's change gets 403 `viewer` without the body being parsed or validated.
3. **Body limits.** 1 MiB by default (Fastify refuses more with 413 before parsing), 12 MiB only on the six `/api/import/*` routes whose `csvText` may be 10,000,000 characters, 8 KiB on the sign-in routes. The default is 1 MiB rather than the 256 KB the audit suggested because a contract-valid plan edit (600 cells with notes) can exceed 256 KB.
4. **List limit.** No list or map in a request may have more than 5,000 items (`MAX_LIST_ITEMS`, checked on the parsed body before its contract: 413 `too_many_items`). Zod 3 validates every element of an over-long array, and the fix for that upstream advisory exists only in Zod 4; this check bounds the work without a major upgrade (decision 117: the test over every route, the residual risk and when to revisit). Lists that had no limit got one: reorder ids and import choices 5,000, tags 50, cash-flow account ids 500, fee columns 10.
5. **Changes must be same-origin and JSON.** For every method except GET, HEAD and OPTIONS (sign-in and sign-out included) the API refuses a request whose `Sec-Fetch-Site` is not `same-origin` or `none`, or, when the browser sends no `Sec-Fetch-Site`, whose `Origin` host differs from the request's own host (403 `cross_site_request`); a client that sends neither header is not a browser and passes. A `Content-Type` other than `application/json` on a change is 415, so no HTML form can be a valid request. The cookie stays SameSite=Lax: Strict would add nothing here, because the threat is a same-site sibling host (another machine on the tailnet name), which SameSite does not stop and the origin check does, and no state changes on GET.
6. **Proxy trust is a list of addresses.** `TRUST_PROXY` names the peers whose `X-Forwarded-For` / `X-Forwarded-Host` are believed (IPs, CIDR ranges, or the presets `loopback`, `linklocal`, `uniquelocal`). The default is nobody; `true` and hop counts are refused, because a client that reaches the port directly could then choose its own address. The compose file sets `uniquelocal` for the web container unless `.env` names the proxy (decision 114): its port is not published, so its only peers are on the compose network, and Caddy replaces any forwarded header a client sends. A fixed subnet for the compose network would be tighter but can collide with networks the server already has, so it was not chosen.
7. **The API binds loopback by default.** `API_HOST` defaults to `127.0.0.1`; the Docker image and the compose file set `0.0.0.0` inside the container. The Vite dev proxy targets `127.0.0.1:3000`.
8. **Sign-in limits per account as well as per address.** Per address (before the body is read): 5 setups, 10 passwords, 10 codes a minute. Per account, whatever the address: 20 password attempts a minute per username, and 5 authenticator codes per 15 minutes per user (480 guesses a day against a six-digit code with a three-step window). A locked-out owner sees how many seconds to wait; existing sessions are unaffected. The counters live in the API process and reset when it restarts. (Decision 13 adds what is kept in the database: the wrong codes counted on each password session.)
9. **What a caller may send is bounded; what the API returns is not.** Requests use `CentsInput` (at most 15 digits of cents, about ten trillion dollars, so thousands of amounts still sum inside a bigint), `IsoDateInput` (a real calendar date, 1900-01-01 to 2199-12-31) and `MonthInput` (1900-01 to 2199-12); responses keep the loose `CentsString`, `IsoDateString` and `MonthString`, so whatever a bank feed or an old import stored still serializes. The API refuses to register a route whose request contract uses a loose shape. CSV imports apply the same bounds per row ("Unreadable date", "Unreadable amount"), and a split ratio side is at most 1,000,000.
10. **A page cursor the server did not issue is 400 `invalid_cursor`** on the transaction, audit and investment-transaction lists (before: a 500 from Postgres, or silently the first page).
11. **Postgres data exceptions are the caller's 400.** A value the database refuses as out of range or malformed (SQLSTATE class 22; for example a quantity times a price that no column can hold) is answered 400 `invalid_value` and logged at warn level, not 500. The contracts stop what they can see; this is the net under them.
12. **Payee search matches `%`, `_` and `\` literally**, through the same `containsPattern` helper as the transaction and security searches.

Authentication and household members (audit batch "auth and users"):

13. **A wrong code costs the password session, and every attempt is on record.** A password-only session counts its wrong authenticator codes in the database and is deleted at the fifth (401 `sign_in_again`: the password has to be entered again, which has its own limits); with decision 8's 5 codes per 15 minutes per user that is at most one such session per quarter hour. Failed passwords on real accounts, a wrong current password typed on a signed-in session (`reauth_failed`, decision 21), wrong codes and the code that ended a session are kept as sign-in activity for 90 days and shown under Settings with a count for the last 7 days (the owner sees every member's, a viewer their own). A member's last completed sign-in is also kept on their row (`user.last_sign_in_at`), so the Members table and the recovery command's `users` still show it once the activity that recorded it is gone. Attempts on unknown usernames are not kept: what is typed there may be a password. A reused code and a wrong code get the same answer (`bad_totp`).
14. **A password-only session lasts ten minutes**, for the code and for first-time enrollment alike; after that the password is asked again. It never becomes a signed-in session: accepting the code (or completing enrollment) creates a new row under a new id and deletes the old one.
15. **A code is accepted once.** The 30-second step of the last accepted code is stored per user and a code is taken only when its step is later, in the same transaction that creates the signed-in session. The one-step tolerance either side stays, so the previous code still matches but is refused once a later one was used. The code that completes enrollment counts as used.
16. **Session ids are stored hashed (SHA-256), and a session is named by that hash** in the session list and when ending one; the id itself exists only in the cookie. Migration 0004 hashes the ids already stored, so browsers that are signed in stay signed in, and deletes password-only sessions.
17. **Two ends for a signed-in session: 30 days (`SESSION_TTL_DAYS`) and 14 days without a request (`SESSION_IDLE_DAYS`, new).** 14 rather than a shorter idle period so that someone who opens the app every week or two is not signed out between visits. `last_seen_at` is written at most every five minutes. Expired rows are deleted by the worker's scheduler once an hour (a plain delete, not a queued job) and, for the member who signs in, at that sign-in. That housekeeping runs after the tick has queued the syncs, the daily jobs and the price jobs, in its own try block: a purge that fails is logged and retried on the next tick, and never keeps anything from being queued. Signing in from a browser that already had a session ends that session.
18. **One owner; the owner adds viewers.** First-run setup takes a Postgres advisory lock and re-checks that no user exists, so concurrent setups create one account. No second owner can be created: the spec names two roles and the schema says one owner; a second owner would be a product change. There is no setup code printed in the log: the first-run window closes with the first account, the database is empty until then, and an owner who finds "Sign in" where "Create the owner account" should be can see who exists with the recovery command `users` and start over. The README says to create the owner right after the first start.
19. **A viewer gets a first password from the owner and enrolls their own authenticator at first sign-in.** The password is not forced to change: the owner already sees everything a viewer sees, and the viewer can change it under Settings. Usernames are unique whatever their case: the column's own UNIQUE is exact, so adding a viewer takes the same advisory lock as first-run setup before it looks for the name in any case, and of two requests for "Pat" and "pat" sent together one is refused (409 `username_taken`). A unique index on `lower(username)` would also hold the rule, but its migration would fail to start the app wherever two such names were already stored.
20. **Viewers may change their own sign-in.** The viewer role refuses every change except routes marked `ownAccount` (own password, authenticator replacement, own sessions). Member management is `ownerOnly`, reads included (403 `owner_only`).
21. **Changing a password ends that member's other sessions** and re-issues the current one under a new id; the current password is required (403 `wrong_password`, counted against the same per-username allowance as signing in and kept as sign-in activity, `reauth_failed`, like a wrong password at sign-in; the same holds where replacing the authenticator and adding a passkey ask for it). The owner setting a viewer's password, clearing a viewer's second factor or removing a viewer ends all of that viewer's sessions.
22. **Replacing an authenticator never leaves the account without one.** The member re-enters the password, gets a new secret, and the old authenticator stays in force until a code from the new one is accepted; then the others' sessions end. Clearing a second factor outright (`/api/users/:id/totp/reset`, or `reset-totp` on the console) is for a lost device: until the member enrolls again their password alone reaches the enrollment screen, so the screens say to do it at once. The owner cannot clear or reset their own account through member management; that is the console's job.
23. **Recovery is a command on the server, not a route.** `apps/api/dist/admin.js` (`users`, `reset-totp`, `reset-password`, `sign-out`) needs a shell in the web container and the database settings only. `reset-password` prints a generated temporary password instead of reading one, so nothing typed ends up in shell history. Its changes are audited with no user.

SimpleFIN sync (audit batch "sync core"):

24. **The high-water mark is the day every account is complete through, and it moves only after a complete response.** `connection.synced_through` used to become today after every HTTP 200, including the ones where the Bridge reported `con.auth` or `act.*` and sent its last known data; once the bank came back, the window started 7 days before that day and everything older was never requested. Now (`highWaterMarkAfterSync` in `packages/shared/src/simplefin.ts`) the mark stays where it was while the response carries a connection (`con.*`) or account (`act.*`) entry, and also while an open account's balance date is more than 7 days old (the Bridge is serving a stale copy without saying so; an account silent for more than 93 days is dormant and holds nothing back, and accounts the household closed are ignored). It is cleared when an account appears for the first time in a window shorter than the first-sync one, so the next sync asks for 93 days and the new account gets the same history as the first ones did (and when one appears in a balances-only refresh, which asks for no transactions at all: decision 115). The mark is kept per connection, not per account: one request serves every account, so the window is decided by the least complete account either way, and a second mark would add state without changing a request. Codes outside `con.*` and `act.*`, and the plain strings in `errors`, are notices and do not hold the mark.
25. **A sync never asks for more than the first-sync window (93 days), and says so when that leaves a hole.** Without a cap, a bank that stays broken would make every sync ask for one more day, for ever. When the mark is older than the window can reach (a bank unreadable, or the worker off, for more than 86 days), the days from 7 days before the mark (where an ordinary sync would have started) to the window are not requested again; the sync records a `sync.gap` entry on the connection and in the import log naming those days, which stays on the Connections page until the household dismisses it (decision 116). A CSV import covers such a period. "Full resync" (Connections page; `fullResync` on `POST /api/connections/:id/sync`) asks for the whole 93 days again; if a sync is already waiting it is turned into a full one, and while one is running the request is refused with 409 `sync_running` rather than answered with a job that would not do it.
26. **An account covered by a problem keeps its pending rows.** `applyAccountSet` no longer reads "not in the list" as "gone" for an account named by `act.failed` or `act.missingdata`, or belonging to a bank connection named by `con.auth` (matched on `conn_id`; every account when the entry or the account does not carry one). A posted item still replaces its pending row in place. The cost is that a hold that really dropped off stays as a pending row until the account is readable again.
27. **Scheduled syncs are spaced from the last attempt, and stop after a refusal.** The scheduler ticks every minute; a connection is due when `last_attempt_at` is older than `SYNC_INTERVAL_HOURS` (before: when the last *success* was, so one failure meant a request a minute). A connection whose last attempt failed gets one try per interval instead of the queue's three, which keeps a failing connection at the request rate of a working one. No longer backoff than the interval: 6 hours already is one, and a Bridge that comes back should be picked up within it. After HTTP 403 (access revoked) or 402 (payment required) the connection is `sync_paused`: nothing is scheduled until a sync started from the Connections page succeeds, or the connection is switched off and on again. Both statuses stay as the plan had them (`auth_required`, `error`); the page says the schedule is paused and how to resume it. A balances-only refresh counts as an attempt, as it always counted as a sync.
28. **A failed sync replaces what the connection shows.** `last_errors` is emptied when a sync fails, so the entries of the previous response do not stand next to the new error. `sync.gap` notices are the exception: they stay (decision 116). Network failures carry the cause Node keeps in `err.cause` ("its certificate was not accepted: self-signed certificate (DEPTH_ZERO_SELF_SIGNED_CERT)", "getaddrinfo ENOTFOUND …", "timeout (no answer within 60 seconds)", "other side closed (UND_ERR_SOCKET)" for a body cut off after the headers) for the Bridge and the price provider alike, whether the request failed or the reading of its body did (for the price provider's body since the batch's second round), as one bounded line with any URL cut down to scheme and host, because an access URL is a password and a claim URL a one-time secret.

Import page (audit batch "import UI"):

29. **The bank CSV preview runs once per change.** The page re-ran the preview from an effect that depended on the mapping object and stored the mapping of every response, a new object each time, so it asked about a hundred times a second and the preview never stayed on screen: no file could be imported from the page. The preview is now a query keyed by its request (file, account, profile, mapping), shared with the Phase 3 positions and trades flows (`useCsvPreview`; Phase 3 audit decision A10 has the details): the server's guess or the profile's mapping becomes the page's once, without a second request, and a response never replaces a mapping the owner has edited. A change the server refuses leaves the last preview and the editor on screen with the commit disabled. After a commit the preview runs again and marks the imported rows as duplicates; the result line counts the duplicates as they were when the import was committed.

SimpleFIN client and response parsing (audit batch "a4-sync-parse"):

30. **A feed amount is a protocol numeric string, read to the cent.** `parseSimplefinAmount` (`packages/shared/src/simplefin.ts`) reads an optional sign, digits with a fraction of any length and an optional exponent ("+5.00", "12.345", "1E+2", "-0.5e1"), rounds half away from zero to the cent and says when non-zero digits were dropped. Anything that is not a number, or has more than 15 digits of cents (the bound of decision 9), cannot be read. The strict `parseDecimalToCents` stays for what the household types. Before, one such value failed the sync for every account after it, and kept failing it until the item was 93 days old (a balance for ever). Now one value costs only itself: the transaction is skipped (`amount.unreadable` for its account), a balance keeps the last known one and writes no balance row (`balance.unreadable`; a new account is created without one), and amounts rounded to the cent are counted (`amount.rounded`). These do not hold the high-water mark: the same item comes back on every request, so asking again cannot help, and holding the mark for it would make every sync ask for 93 days. The raw payload is kept, and a full resync after an update reads the item again (Re-read transactions, decision 53, reaches items older than 93 days). An account with a skipped transaction keeps its unmatched pending rows, because its list is not the whole list.
31. **A response is stored before it is read, whatever its shape.** The client returns the parsed JSON without judging it; the sync job writes it to `import_log.raw_payload` and only then reads it (pipeline step 2). A 200 that is not JSON is stored as `{ "notJson": <text> }` next to the error. NUL characters and unpaired surrogates, which Postgres `jsonb` refuses (one NUL in a description failed the sync and lost the payload), become U+FFFD in every string and key (`jsonbSafe`). The stored copy is also the one that is read, so an id with a NUL in it is the same id on every sync. Nesting deeper than 1000 levels is cut off in that copy, since the value could not be written otherwise (decision 123).
32. **A response is read one entry at a time.** `readSimplefinAccountSet` reads each account and each transaction on its own. Optional text may be null, amounts may come as JSON numbers, `holdings` and `extra` take any shape (the holdings parser decides what it can read, imports design §3.3), timestamps must be 0 or within 1970 to 2199 (an optional one out of range reads as absent), and an `errlist` entry is never dropped (one without a code reads as `unknown`). An account that cannot be read is skipped with an `account.unreadable` entry and holds the mark as `act.failed` does, since it sent none of its transactions, unless the household closed it; a transaction that cannot be read is skipped and counted for its account (`transaction.unreadable`). Only a body that is not an account set (not an object, or `accounts` missing, null or not a list; decision 122) fails the sync, with its payload kept. `errors` and `errlist` that are not lists are read, not refused (decision 122). `simplefin.reprocess_holdings` reads stored payloads the same way.
33. **Transactions are dated by `transacted_at`.** The protocol's optional `transacted_at` (when the transaction happened) comes first, then `posted`, then, for a pending item with neither, the household's day (the day it was first seen: a stored row keeps it, decision 108). The schema used to read `transaction_date`, which the protocol does not have, so posted items took their post date and pending ones the sync's clock, and late-month spending landed in the next month. Timestamps stay UTC dates, as the Bridge dates them. The sync's "today" (its window, the mark and the pending fallback) is the household's day (Phase 2 plan decision 16); the holdings' future-date check keeps the later of the household's and the UTC day.
34. **The accounts that need transactions are the open ones.** An account the household closed still gets its balance and holdings from the feed, but no transactions, and an `act.*` entry naming it does not hold the mark (decision 24 already ignores closed accounts for the stale-copy check). The request itself is not filtered with `account=`: a filtered request would hide an account added at the Bridge, which decision 24's new-account rule needs to find, and the Bridge limits requests rather than the accounts in them, so the filter would buy little. This meets the spec's "requests only accounts that need transactions" in what is ingested rather than in the request (flagged under Deviations). Closing a feed account is asked first, and reopening it replays the stored responses, so the days it was closed are not lost (decision 91).
35. **Error text is sanitized and bounded wherever it is stored for display.** `errorMessageText` (`sanitizeText`, at most 300 characters) is applied before writing `connection.last_error`, `import_log.message` and every job's `last_error`, because an error can quote what a server sent (a database error quotes the value it refused). The sync's own entries never quote a raw value; they name the field and the account.
36. **A plain string in `errors` that repeats an `errlist` entry is shown once.** The comparison is with the entry's sanitized `msg` as well as its decorated message, so a Bridge that sends the same text in both lists no longer shows each problem twice.
37. **A setup token whose claim failed for a reason that passes can be claimed again.** The claim job keeps the token after any failure except a 403 and an access URL it refused, both of which spend the token, and the connection says "The setup token could not be claimed yet: …. Press Sync now to try again." `POST /connections/:id/sync` queues the claim (status `claiming`) whenever a token is stored and there is no access URL, whatever the status; before, a claim that failed three times (a Bridge outage of about six minutes during setup) left a connection that could never be claimed. With neither a token nor an access URL, the 400 `no_access_url` says to remove the connection and add it again with a new setup token, since no route puts a new token on a connection.
38. **A job a dead worker left behind counts as a failed attempt.** `requeueStaleJobs` fails a job whose attempts are spent and puts any other back after the backoff `failJob` gives (2, 4, 8 … minutes, at most an hour). Before, it went back at once with no limit, so a response that ended the worker (for example one too large for its memory) ran again every half hour for ever. A SimpleFIN job's open import log rows are closed as errors, and a sync's connection records the attempt as a failed sync does (status `error`, `last_attempt_at`), so the scheduler spaces the next one from it and gives it a single try (decision 27).
39. **Responses are read up to a limit.** The worker reads at most `SIMPLEFIN_MAX_RESPONSE_MB` (default 50) of an account-set response and 64 KB of a claim answer, by the declared length or while reading. A larger one fails as `too_large` and is not retried within the job (the same request gets the same answer); the next scheduled sync tries again, and the schedule is not paused. A timeout or a dropped connection while the body is being read is a network failure that says why (decision 28: "timeout (no answer within 60 seconds)"), not "not JSON".
40. **Outbound SimpleFIN calls go only to allowed hosts** (spec, Security: outbound calls limited to the SimpleFIN host). A claim URL's host must be in `SIMPLEFIN_ALLOWED_HOSTS` (default `bridge.simplefin.org, beta-bridge.simplefin.org`), checked before any request, and the access URL the claim returns must be on the claim's host; every sync checks the access URL's host again. A token for any other host (a LAN address, a forged token) is refused without a request and kept, so that once the host is listed and the worker restarted, Sync now claims it; an access URL on another host is not stored and the token counts as spent. Private and loopback addresses are refused like any other host that is not listed. The API checks only the token's shape: the worker makes the call, so the worker enforces the list. The Bridge's host names come from the public protocol documentation and could not be checked from the build container; a household whose Bridge answers on another name lists it.
41. **Invisible formatting is stripped from server text.** `sanitizeText` also removes the bidirectional embeddings, overrides and isolates (U+202A to U+202E, U+2066 to U+2069), the left-to-right, right-to-left and Arabic letter marks, the zero-width space, the word joiner and invisible operators (U+2060 to U+2064) and the byte order mark: a right-to-left override in a payee could show "00.005$" as "$500.00". The zero-width joiner and non-joiner stay, because emoji sequences and some scripts need them and they reorder nothing.

Ingest, pending replacement, transfers and duplicates (audit batch "a5-ingest-transfers"):

42. **One purchase is one row, whichever source brings it.** Before, duplicates were matched only on the external id, and a CSV row's id (a content hash or the bank's CSV id) never equals a SimpleFIN id, so a bank export over synced days doubled every overlapping row (and the plan, the review count and the cash flow with them). Now two rows of one account are the same purchase when their amounts are equal, their dates are at most 5 days apart (`DUPLICATE_MAX_DAYS`: a bank's export dates by posting, the feed by `transacted_at`) and their descriptions share something (similarity above 0); the best similarity wins, then the closest date, and each row is taken once (`findSameTransactions`). A CSV row that is the same purchase as a feed row (pending or posted) or a manual one that no other CSV id points at is not inserted: its id goes to `transaction_alias`, pointing at that row, so a re-import and the preview know it. A posted feed item that is the same purchase as a CSV or manual row takes the row over (its id, source, date, description, memo and post time; the household's payee, category, notes, tags and split stay) and the row's old id is kept, so the file's next import knows it; a pending feed item that is the same purchase as a posted CSV or manual row points at it and is ignored while it stays pending. A CSV row no longer replaces a pending feed row in place (it matched every pending row of the account, of any age, and took its id away from the feed); it points at it, and the feed's posted item replaces the pending row as before. The Import page's duplicates are computed by the same rules (`csvDuplicateIds`), so the preview marks what the commit will skip. Within one source the ids still decide: two coffees of one amount on one day from the feed are two rows, and a CSV row is matched to another CSV row only when their ids are of different schemes, by its content (decision 105).
43. **A reconnected bank is the same accounts.** Removing a connection keeps its accounts without one, and their stored responses (decision 107; the Connections page says so, and decision 37 tells the household to remove and add a connection again). An account the feed names that is not on the connection, but that an account without a connection carries the id of, is attached to the connection (`upsertSimplefinAccount`, `accountsReattached`; it counts as a new account for the mark of decision 24), so its rows are found by id and nothing is doubled. A feed that re-keys an account's transaction ids is recognised when none of the account's posted feed rows in the window is listed by id any more while the feed sends posted items: those rows are then candidates for decision 42's match and are taken over by the new ids (the old ids are kept). The test is off for an account the Bridge reported a problem with (its list may be partial); its cost is that a Bridge that silently left out every posted row of an account in the window would have new purchases matched to them. An account the Bridge re-issued under a new id, or one whose history came from CSV files before the bank was connected, is linked by hand: **same as a feed account…** on the Accounts page (`POST /api/accounts/:id/link-feed`, `linkFeedAccount`) makes the account without a connection the one the feed fills (its connection and id), folds the feed account's rows in (dropped when the account has the id, taken over by the account's row when it is the same purchase, moved otherwise), copies balances it lacks, moves recurring items, goals, the cash-flow account and card payment settings, drops the feed account's own holdings snapshots (the next sync writes them again) and removes it. Refused when the account has a connection (409 `account_connected`), the other account is not from a feed (400 `not_feed_account`), or the feed account holds investment history of its own (409 `feed_account_has_history`). Audited as `account`.
44. **Every pending row of an account is a candidate, and one the feed stopped returning is removed whatever its date.** The window was `synced_through − 7 days` and pending rows were considered only from 7 days before that, so a hotel or car-rental hold pending for two to four weeks was never replaced when it posted (both rows counted) and one that dropped stayed for good (the cash flow's opening balance counts pending rows). The feed's list of pending items is not bounded by the start date (`pending=1` asks for every pending item), so a pending row the feed does not return has posted or dropped, however old it is. Decision 26 still applies: an account the Bridge reported a problem with keeps its pending rows. Flagged assumption: if a Bridge did bound pending items by the start date, a hold older than the window would be removed and come back with the next full resync.
45. **A pending charge may post for another amount.** After the equal amounts, a posted item still unmatched may take a pending row of the same merchant (similarity at least 0.5, `STRONG_SIMILARITY`) whose amount is in the same direction and within half of it either way (50 % to 150 %): a tip, a hotel or a fuel hold that settled for another amount. The closest amount wins, then the date. The row keeps its id, category, notes and tags; a split is dropped as for any bank amount change, and a transfer pair is released (no longer equal and opposite). A hold that settles below half of itself (a $1 authorization) is not matched: the posted row is new and the pending row goes.
46. **A pending row is replaced only by a posted item that shares something with its description.** A posted "COSTCO WHSE" of the same amount within 5 days took over a pending "SHELL OIL" row with its locked payee, category and notes (similarity 0 was enough). Now the descriptions must share a normalized token or be the same payee; otherwise the posted item is new and the pending row goes as any vanished one.
47. **A pending item listed next to its posted form is one row.** When the feed still lists a pending item (by its id) and also its posted form under a new id, the posted item replaces the pending row in place when the amounts are equal and the descriptions match strongly, and the pending id goes to `transaction_alias`, so it is ignored for as long as the feed keeps listing it. Two new items in one response (a first sync that holds both forms) are both kept until the pending one drops: on a first sync a pending and a posted purchase of one amount at one merchant are as likely two purchases.
48. **"transfer · undo" lasts, and a hand categorization wins over pairing.** Undoing a pair records the two rows in `transfer_dismissal`; the pairing pass never pairs them with each other again (each may still pair with another leg). A row the household categorized by hand (`category_locked`, a split included) is not a pairing candidate unless it is marked as a transfer, in line with "automation never overrides a hand categorization". Before, any later sync or CSV commit paired the rows again and took their categories out of the plan. Pairing by hand (decision 52) removes a dismissal.
49. **A pair id always names two rows.** Before a row that is paired is removed (a pending leg the feed dropped, a row the household deletes, an undone import, a folded feed account), its partner is released: pair id and `is_transfer` cleared, then the rules run on it again (a rule that marks it a transfer or gives it a category still does). The sync's pairing pass runs whenever a partner was released and covers its date, so the posted leg that arrives later pairs with it. Before, the partner kept the old pair id, could never pair again and the card payment counted as spending.
50. **A row can be deleted and an import undone.** `DELETE /api/transactions/:id` (the register's **more** → delete) removes a manual, CSV or feed row, releases its partner, unlinks it from a recurring item and is audited (`transaction`). The ids of a feed or CSV row (its own and those pointing at it) stay in `transaction_alias` with no row, so the next sync or a re-import does not bring it back. Investment rows are refused (400 `investment_row`): they belong to the investment flows. `POST /api/import/csv/:id/undo` (the Import page's **Undo this import** on the result line; the commit now returns its `importLogId`) deletes the rows a bank CSV import created that are still CSV rows (one the feed took over since is the feed's), releases their partners, forgets the ids it recorded for rows the ledger had, and marks the import log `undoneAt`; the file can then be imported again. 409 `already_undone`; audited as `import_log`.
51. **Pairing finds as many pairs as the legs allow.** Each outflow still takes the closest free inflow; when every inflow it can reach is taken, an earlier outflow gives its inflow up if it can take another one within the window (an augmenting path). A same-day checking → savings → brokerage move of one amount pairs both hops whatever the row ids are (before, about one time in four a hop was left as uncategorized income and spending).
52. **Pairing by hand.** **more** on a register row lists the rows it could be paired with (equal and opposite, another account, within 14 days, not paired; `GET /api/transactions/:id/transfer-candidates`, pairs the household undid included) and pairs it with one (`POST /api/transactions/:id/pair`: one pair id on both, `is_transfer`, a category automation gave them goes; 400 for one account or amounts that are not equal and opposite, 409 `already_paired`; audited). **mark as a transfer without its other leg** sets `is_transfer` and now also clears a category automation gave the row (a hand-picked one stays, as with pairing).
53. **Stored responses can be replayed for their transactions.** `simplefin.reprocess_transactions` (`POST /api/connections/:id/reprocess-transactions`, **Re-read transactions** on the Connections page) replays every stored sync payload of the connection, oldest first, a page at a time: posted items the ledger lacks are inserted, or recognised as rows it has under another id or as rows the household deleted; a row it has is left as it is (the live feed keeps it current, and a split must not be dropped by an older amount); pending items are never inserted and no pending row is replaced or removed; accounts, balances and holdings are not touched. Running it twice changes nothing. It reaches days older than the 93 days a full resync can ask for (decision 30 relies on it).
54. **Rules at import see the payee the name resolves to.** A new row's normalized name is looked up through payee aliases first (`PayeeCache.find`, which creates nothing) and the rules are evaluated against that payee's name, as `applyRulesToRow` does on demand and on a replaced pending row. A rule on a merged payee ("Starbucks Store", alias "Sbux Mobile Order") applies to every variant at import.

Accounts, payees, rules and text safety (audit batch "a6-text-rules-accounts"; record in `docs/audit/phases-1-3/a6-text-rules-accounts.md`):

55. **Rule patterns run on RE2.** A rule's regular expression is matched by `re2js` (a JavaScript port of RE2, pinned exactly: 2.8.6, 2.8.7 since decision 119), whose time is linear in the text whatever the pattern, so `^(\w+\s?)+$` cannot hang the API or the worker's sync (it took minutes on a 44-character description with the JavaScript engine). Patterns are compiled once per batch. RE2 has no look-around and no back-references; a create or an edit with a pattern RE2 refuses, or one longer than 200 characters, answers 400 `invalid_regex` with the reason, and a stored pattern RE2 refuses never matches. A time budget in a worker thread was the other option; it would still spend the budget on every row of every import.
56. **A rule is saved as it will run, or refused.** An amount condition needs a minimum, a maximum or both, and the minimum may not be above the maximum (400 `invalid_amount_range`; amounts are signed). A day-of-month range whose start is after its end wraps past the month end (28 to 3), and a day past the end of a month means its last day (31 matches 30 November and 28 February). The stored contract stays loose, so a rule saved before these checks still lists and can be edited.
57. **A category a rule sets is in use.** `DELETE /api/categories/:id` answers 409 `in_use` naming the rules (up to three) whose action sets it, as it does for transactions, splits, recurring items and goals. Rules are validated on create and edit (400 `unknown_category`). A rule left from before, whose category is gone, sets nothing: `loadRules` drops that action for evaluation (its other actions still apply), so an import or a sync never fails on the foreign key; the Rules page shows the action as "(deleted category: sets nothing)".
58. **A payee condition holds on the payee's other names.** The rules see a row's payee name and its aliases (the names merged into it and its earlier names), at import, on demand and when a transfer partner is released, so a rule written on "Sbux Mobile Order" keeps working after that payee is merged into "Starbucks Store" and after a rename. A rename keeps the old name as an alias, and a name another payee has, as its name or an alias, is 409 `name_taken` (merge instead). A rule that sets the payee clears the aliases for the rules after it. The Payees page (new) renames, merges and sets the default category.
59. **Text is compared in one spelling.** `sanitizeText` stores NFC. Case-insensitive rule matching compares NFKC text with the accents of Latin letters folded ("Café" equals "cafe", "İSTANBUL" contains "istanbul"); case-sensitive matching compares NFC. `normalizePayee` keeps letters of every script (the token trim and title case are Unicode-aware) and folds Latin accents, so "Café Rio" and "CAFE RIO #23" are one payee; a rename restores the spelling the household prefers.
60. **The city is what follows the store number.** A store number, phone number, masked card or processor code marks where the merchant ends: the words between it and a trailing state code (none to three) are the city and are dropped, and when nothing stands between them only the state goes ("TACO BELL 1234 CO" is Taco Bell). Without such a mark the city is the last word, widened by short lists of city prefixes (SAN, LAS, NEW, FORT, ST, SALT …) and suffixes (CITY, SPRINGS, RANCH …). A weekday before a time and hour-only times ("TUE 5PM") are dropped. A bare "ST LOUIS BREAD CO" still reads CO as the state; a rename (decision 58) corrects such a name once. New rows only: rows already stored keep their payee, and a merge folds the old and the new name.
61. **`sanitizeText` leaves no angle bracket and bounds its work.** The input is cut to four times the length cap plus 256 characters before any pattern runs, complete tags are removed with a linear pattern (`<[^<>]*>`), and any `<` or `>` left is removed, so an unclosed tag in a feed's account name cannot open markup where HTML is set; a cut never splits a surrogate pair. The chart tooltips (cash flow, Portfolio, Performance) also escape every name they put into their HTML, whatever its source.
62. **Previews show sanitized cells.** The bank, positions and trades previews return their headers and sample cells through `sanitizeText` (at most 100 characters each); a mapping is resolved by the sanitized header name (`headerKey`), so a mapping built from what the preview shows still finds a header that carried a control character. The bank importer quotes a bad date at most 50 characters, sanitized.
63. **A manual account's balance is recorded by date.** `POST /api/accounts/:id/balances { balanceCents, date? }` (default the household's today; **update balance** on the Accounts page) writes a manual `balance_snapshot` for an account without a bank connection and becomes the account's balance when no later one exists; an earlier date goes into the history only. Refused for a feed account (409 `feed_account`) and a date after today (400 `future_date`); audited as `account`. `PATCH /accounts/:id` refuses keys it does not take (400), so a balance sent there is no longer dropped silently. A new manual account's balance is dated by the household's day on the API clock, not the machine's UTC date.
64. **A loan's balance is what it owes, as a negative amount.** The Accounts page asks a card or a loan for the amount owed and stores it negated; the API refuses a positive balance for a manual loan (400 `debt_balance_positive`), at creation and by date. A card may be in credit, so its sign is not checked. Amounts are read with string math ("1,234.56", "$500"; "1.005" is refused with a reason, never dropped).
65. **Assets and loans start off budget.** `defaultOnBudget` (both creation paths) puts asset and loan accounts off budget, beside the investment types (Phase 3 decision 15), so a house or a mortgage is not cash in the cash-flow projection or the dashboard's 30-day line; checking, savings and cards start on budget. Existing accounts keep their flag; the Accounts page's Budget column switches it.
66. **A feed account's type follows its noun.** `guessAccountType` decides by the account noun first: "Joint Checking", "Kasasa Rewards Checking", "Student Checking" are checking, "Auto Savings" savings; investment and retirement words come before that, card and loan words only when no bank noun is present, and "Individual" or "Joint" alone name a brokerage.
67. **Rule positions are 1..n, and a deleted rule comes back in its place.** Creating, restoring and reordering rules take one advisory lock, so concurrent creates get consecutive positions. `POST /api/rules` takes `position` (the rules from there move down one when the place is taken, audited) and `enabled`; the Rules page's history (`GET /api/audit?entity=rule`) reverts an entry through the normal routes: a deleted rule is created again at its old position, in its old state, with `applyTo: "none"`; an edit is sent back with PATCH; a move goes back with a reorder; a create is undone by a delete. The page also has a rule editor with every condition and action, and asks before deleting. A rule name over 100 characters is cut with "…" instead of refused, so "always do this" works on a long payee name.
68. **The repository root holds only the workspace.** The stray root `src/` (early copies of the API tests that could not run) and `KICKOFF.md` (the original Phase 1 prompt, superseded by `CLAUDE.md` and this plan) were removed; git history keeps them.

Backups, deployment and secrets (audit batch "a7-backup-deploy-secrets"; record in `docs/audit/phases-1-3/a7-backup-deploy-secrets.md`):

69. **A backup counts only when it reads back.** The backup service is built from `deploy/backup.Dockerfile` (the Postgres image plus `openssl`, `rclone`, `openssh-client` and `su-exec`; the stock image has no `openssl`, so every nightly backup had been written empty while the log said it worked). `backup.sh` records the exit status of each stage of `pg_dump | gzip | openssl` (busybox and dash have no portable `pipefail`), then decrypts and gunzips the new file and requires pg_dump's `-- PostgreSQL database dump complete` line before it moves the file into place. A failed backup leaves no file, promotes nothing and prunes nothing, is logged as `FAILED: …` and exits non-zero; the nightly loop runs each backup as its own process; start-up refuses a missing tool or setting, so the container restarts and shows it. `umask 077`: files 0600, folders 0700. The container starts as root only to hand `/backups` to `postgres` (uid 70), then drops to it.
70. **A restore never destroys what it cannot replace.** `restore.sh` reads the whole backup first (decrypt, gunzip, closing line), then restores into a new database with `psql -v ON_ERROR_STOP=1 --single-transaction`, checks that it holds the app's migrations, and only then renames the current database to `<db>_before_<time>` (kept until the household drops it) and the restored one into its place. Replacing asks for the database name, or `--yes`; `--target-db <name>` restores beside the live database; `--check` restores into a throwaway database and drops it. Settings that are not already set are read from the repository's `.env`, found from the script's location, as text: the file is never executed. It runs in the backup container (`docker compose exec backup /restore.sh …`), which has the tools and the database's network now that the database port is not published (decision 76).
71. **The off-site copy is part of the backup.** `BACKUP_COPY_CMD` runs for every backup file, daily and monthly, that has not been copied yet (`$1` the file, `$2` its folder), so a file whose copy failed is tried again after the next backup. A failure makes the run exit 3, is recorded in `status/offsite` and fails the healthcheck. rclone and scp are in the image; their configuration and keys go in `deploy/backup-config/` (mounted, git-ignored).
72. **A restore check exists now; its schedule is Phase 6.** `restore-check.sh` restores the newest (or a named) backup into a throwaway database on the same server through `restore.sh --check`, counts migrations, tables, members, accounts and transactions, drops it and writes `status/restore-check`. A throwaway database rather than a throwaway container: the backup container has, and should have, no access to the Docker socket, and the database proves the same decrypt, read and restore. The spec lists restore-test automation under Phase 6, so the monthly schedule is not added here; the README says to run it monthly.
73. **SECRETS_KEY is checked at start-up.** Both the API and the worker refuse a key that is not 32 bytes of standard base64, naming what it is (a 64-character hex key from `openssl rand -hex 32` "decodes to 48 bytes"). After migrations they try the key on every stored secret (a handful of rows) and refuse to start when it opens none of them ("SECRETS_KEY is not the key these secrets were encrypted with …"); when only some fail, they start and log which. No key-check value is stored: the stored secrets already are the check, and no migration is needed. A decryption failure anywhere says "could not be decrypted with SECRETS_KEY" instead of Web Crypto's "operation-specific reason".
74. **The key can be changed, and recovered from when it is lost.** `admin.js rotate-secrets-key` re-encrypts every `*_enc` column from `SECRETS_KEY_OLD` to `SECRETS_KEY` in one transaction (a value neither key opens stops it; a value already under the new key is skipped, so it can run twice); a test keeps `ENCRYPTED_COLUMNS` equal to the schema's `*_enc` columns. `admin.js reset-secrets-key` lists what the current key cannot open and, with `--confirm`, clears it: authenticators as `reset-totp` does, and connections lose their access URL and token, are paused and say to be added again with a new setup token. Both are audited (`connection` joined the audit entities). The ciphertext format keeps no key id: one key is in force at a time, and the rotation is how it changes. `SECRETS_KEY_OLD` is passed to the web container only.
75. **Each container gets only the settings it reads.** `deploy/docker-compose.yml` includes `deploy/services.yml` with `env_file: ../.env`, which makes `.env` the source of compose interpolation (it was not: `BACKUP_HOUR` from `.env` was overridden by the compose default), and every service lists the names it reads (`- NAME`). Caddy gets `SITE_ADDRESS` alone; `SECRETS_KEY` reaches web and worker, `SESSION_SECRET` web, the Tiingo key the worker, `BACKUP_PASSPHRASE` the backup container. A test fails when the API or the worker reads a setting the compose file does not pass. `.env` stays the default home of `SECRETS_KEY` (the spec allows a Docker secret or an env file); `deploy/docker-compose.secrets.yml` is the tested Docker-secret option for `SECRETS_KEY` and the Tiingo key.
76. **Only Caddy publishes ports.** The database's loopback port moved to `deploy/docker-compose.dev.yml` for development; the test checks every service.
77. **db and web have no route out.** They are on an `internal: true` network; the worker and the backup container are also on `egress`, Caddy on `edge` (published ports need a network that is not internal). Which hosts the worker calls stays enforced in its code (`SIMPLEFIN_ALLOWED_HOSTS`, the price provider's host).
78. **Every service has a healthcheck.** Backup: `backup.sh --health` (the last backup failed, no verified backup for `BACKUP_HEALTH_MAX_AGE_HOURS`, default 26, or the off-site copy failing). Worker: a heartbeat file (`WORKER_HEARTBEAT_FILE`) written after every pass over the queue and every job, stale after 35 minutes (the longest job is cut off at 20). Caddy: its admin endpoint; the proxy waits for a healthy web. The backup state is not shown in Settings: the API cannot see the backup volume, and showing it is left for Phase 6 with the scheduled restore test.
79. **Containers run unprivileged.** The API and worker images end with `USER node` (`/app` stays root-owned); the backup container drops to `postgres` as in decision 69.
80. **Image pins are the household's choice, made in `.env`.** Every `FROM` and `image:` goes through `NODE_IMAGE`, `POSTGRES_IMAGE` or `CADDY_IMAGE` (default the floating tags `node:22-alpine`, `postgres:16-alpine`, `caddy:2-alpine`). The repository does not ship digests: it cannot look them up where it is built, and a digest nobody moves stops security fixes, so the README says how to pin and update. pnpm is pinned by version and sha512 in `packageManager`.
81. **Placeholders do not run in production.** With `NODE_ENV=production` the API refuses `SESSION_SECRET=change-me-to-64-random-hex-chars` and both the API and the worker refuse the database password `change-me`; `.env.example` leaves `SESSION_SECRET` empty. Development keeps the example's database password.
82. **Secret files stay out of git.** `deploy/secrets/` and `deploy/backup-config/` are ignored.

The web app's shell, layout and PWA (audit batch "b8-web-layout"; record in `docs/audit/phases-1-3/b8-web-layout.md`):

83. **The last known auth status stays on screen.** App renders from the auth status whenever one was loaded, also while a refetch of it fails (TanStack Query keeps the data and reports the error), so one dropped request, a 502 while the `web` container restarts or a reconnect that fires before the phone's network is up no longer replaces the open page, and what is typed in it, with a full-screen error. Phase 1 conformance (audit batch "a10-conformance-ledger"; record in `docs/audit/phases-1-3/a10-conformance-ledger.md`):

104. **The ledger takes one ingest at a time.** Nothing ordered the CSV commit (in the API) and the sync (in the worker): each read the other's rows before they were committed, so a file over the days of the first sync, which decision 25 tells the household to import, doubled every purchase (60 rows for 30 when both ran at once), and two pairing passes could pair one leg twice. Everything that decides from the rows it reads whether a row is new, the same purchase as another or a leg of a transfer now takes one transaction-scoped Postgres advisory lock first (`lockLedger`, `packages/db/src/services/ledgerLock.ts`): `ingestTransactions` (feed, bank CSV, the trades importer's cash rows, replay), the pairing pass, pairing by hand, a rule run's batches, a transfer marked, undone or a category picked by hand, deleting a row, undoing an import and folding a feed account. One lock for the whole ledger rather than one per account, because pairing and the release of a partner cross accounts and a second key would make an order to keep; ingests are short (one account's rows per transaction) and a household's writers are few, so the wait is unnoticeable. The lock is re-entrant inside one transaction, so the nested calls (an import that pairs, a trades commit that ingests) cannot wait on themselves. Reads (the register, the CSV preview) do not take it.
105. **A CSV row's content id hashes the text as the file has it, and across id schemes the content decides.** The id of a row without a bank id hashed `normalizePayee`'s output, so a change to the payee heuristics (decision 60) changed the id of rows already imported and the next import of the same file added them again; and the same file read once with its id column (`csvid:`) and once without was never matched, because a CSV row was never compared with another CSV row. Now (`packages/shared/src/csv.ts`): rows without an id get `csv2:` + SHA-256 of date, cents and the raw cell in NFC with white space collapsed and in lower case (`csvIdText`), which no heuristic and no sanitizer change can move. Ids name their scheme (`csvIdScheme`: `csvid`, `csv2`, and `csv` for ids made before this decision, which stay as they are: no migration re-keys them, since the old hash cannot be recomputed for an id kept for a feed row, whose own text is the feed's). Within one scheme the ids still decide (two equal coffees in one file stay two rows). Across schemes `findSameTransactions` matches by content, in this order: a CSV row of another scheme with the same date, the same amount and the same description (similarity at least `STRONG_SIMILARITY`); a feed or manual row no CSV id names (decision 42); a feed or manual row that only ids of another scheme name. Each row is taken once, so a third equal purchase in a later file is still added. The preview's duplicates (`csvDuplicateIds`) use the same rule, and an undo forgets the ids an import recorded this way. Cost, accepted: when the id column changes between two files, a purchase in the newer file that the feed does not have can be taken for a feed row of the same amount and merchant within 5 days that the older file named, and is then not added.
106. **A rule's "not a transfer" holds over pairing.** The rule set `is_transfer = false` at import, and the next pairing pass paired the row anyway; run on demand on a paired row it left the pair id on the row and on its partner, which stayed out of the budget while the row counted as income. Now the rule's choice is kept with the row (`transaction.not_transfer`, set when a rule says "not a transfer", cleared when a rule says "transfer"), and the pairing pass skips such rows, as it skips rows categorized by hand (decision 48). Run on a paired row, the rule undoes the pair: the row loses its pair id and its partner is released (pair id and `is_transfer` cleared, the rules run on it again), and a rule run that released a partner ends with a pairing pass over its dates, so the partner may pair with its real other leg. Marking the row a transfer by hand, or pairing it by hand, clears `not_transfer`: the household's choice wins over the rule's. Migration 0009 marks the rows left as the old code left them (`is_transfer` false with a pair id) as ruled out and releases every pair that is not two equal and opposite transfers (also those decisions 104 and 109 describe); a released leg the household did not categorize gets its payee's default category back.
107. **Removing a connection or a CSV mapping profile keeps its import logs.** `import_log.connection_id` cascaded, so removing a SimpleFIN connection deleted every stored response (spec, sync flow 6: kept "for debugging and re-processing"; decisions 53 and 91 replay them) and deleting a CSV profile deleted its imports' logs, after which **Undo this import** answered 404. The key is now `ON DELETE SET NULL` (migration 0009). When the accounts of a removed connection come back on a new one (decision 43), the new connection takes over the stored responses that list one of its accounts (`upsertSimplefinAccount`), so Re-read transactions and reopening a closed account replay them there too; responses that list none of its accounts stay without a connection. The Connections page asks before a profile's Delete and both prompts say what stays. The claim's import log never held the access URL, so nothing secret is kept.
108. **An undated pending item keeps the day it was first seen.** A pending item with neither `transacted_at` nor `posted` is dated by the household's day (decision 33), and every later sync moved the row to that sync's day, so a hold pending for weeks (decision 44) drifted into the next month and, when it posted with its real date, was too far from the row to replace it in place: the household's note and category were lost with the deleted pending row. Such an item is marked `undated` (`toIncomingTransaction`) and a stored row keeps its date; an item that gains a date takes it. The replacement window is not widened: the day first seen is close to when the purchase happened.
109. **A paired row whose amount changes under the same id releases its pair.** The known-row path updated the amount (and dropped a split) but kept the transfer pair, so a checking −500.00 paired with savings +500.00 that posted at −450.00 left $50 unaccounted for. 110. **A row entered by hand is checked before it is written.** `createManualTransaction` (POST `/api/transactions`, decision 93) refuses a zero amount (400 `zero_amount`), a date after the household's today on the API clock (400 `future_date`), an unknown account (404) and an unknown category (400 `unknown_category`); an edit to an unknown category (PATCH `/api/transactions/:id`) and an unknown default category for a payee (PATCH `/api/payees/:id`) are 400 `unknown_category`. 111. **A decimal comma is refused, not read as thousands.** `parseLooseMoney` read every comma as a thousands separator, so "12,50" became 1,250.00 and "1 234,56" 123,456.00 without a word. A decimal-separator option in the mapping was the other choice; the household's banks are US banks, and a refusal cannot put a wrong amount in the ledger.
112. **Passkeys are an optional way to sign in** (spec, Security and backups: "local login with Argon2id-hashed password plus TOTP; optional passkeys"; nothing had been built or deferred). The password and the authenticator stay, so a passkey is never the only way in; clearing a member's second factor (owner's **clear** or `admin.js reset-totp`) also removes their passkeys, because a lost phone may hold them; removing a member removes theirs. Passkeys as a second factor after the password (instead of the code) were the other reading of "optional passkeys"; a passkey with user verification is already two factors, and asking for the password before it would add a phishable step to the one sign-in that cannot be phished.

SimpleFIN client and response parsing, second round (audit batch "a4-sync-parse"; record in `docs/audit/phases-1-3/a4-sync-parse.md`):

122. **`errors` and `errlist` never fail a response, and a response without a list of accounts is not an answer.** Decision 32 read every account and transaction on its own, but a non-list `errors` or `errlist` still threw, so `{"errors": "Scheduled maintenance tonight", "accounts": [...]}` failed every sync while the Bridge kept that shape. Now a single value is a list of one: a message in `errors` is one entry (a value that is not a message reads as absent, as such an element of the list already did; `errors` never hold the mark); an object or a message in `errlist` is one entry, read by the rules of the list's entries, so a bare `act.failed` holds the mark as it would in a list. An `errlist` that is neither a list, an entry nor a message (`true`, `42`) is reported as `errlist.unreadable` and treated as a connection problem: the accounts are applied, every account keeps its unmatched pending rows, and the mark does not move. The other way round, `accounts` missing or null was read as an empty list, so a 200 such as `{"errors": ["Temporary failure, try later"], "accounts": null}` or `{"message": "Service temporarily unavailable"}` counted as a complete, empty response and moved the mark past days earlier syncs may have missed. Such a body is now not an account set (`accounts: missing`): the sync fails as `invalid_response` (retried, as before), the payload is kept, the mark stays, and the error quotes what the Bridge said (the errlist entries as the connection would show them, then the plain messages that do not repeat one, sanitized, at most 200 characters). `accounts: []` is still an account set. Payloads stored before this change without a list of accounts count as unreadable for Re-read transactions and the holdings replay; they held no accounts.
123. **The stored copy of a response keeps at most 1000 levels of nesting.** `jsonbSafe` copied a body of any depth (decision 31), but the database driver's `JSON.stringify` overflows the stack at about 6,000 levels and Postgres refuses `jsonb` nested 20,000 deep ("stack depth limit exceeded"), so a 40 KB body of nested lists, well under the size limit (decision 39), failed the sync with "Maximum call stack size exceeded" and lost its payload. A list or an object deeper than `JSONB_SAFE_MAX_DEPTH` (1000; the body itself is level 1) is now replaced in the copy by the text `[not kept: nested more than 1000 levels deep]`. A SimpleFIN account set is about six levels deep and the holdings in `extra` a few more, so nothing a sync reads is cut off; the marker says where the rest was. Keeping the body as text next to the `jsonb` was the other choice; it needs a column and keeps nothing a sync or a replay could use.
