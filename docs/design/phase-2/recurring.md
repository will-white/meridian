## summary

Recurring detection is a pure, deterministic engine in packages/shared (schedule.ts: calendar schedule primitives; recurringDetect.ts: scoring, amounts, clustering, trial rule, subscription math) driven by one worker job `recurring.detect` that always does a full run over a 36-month lookback (cheap for one household, trivially idempotent). Charges are grouped by (payee_id, sign of amount), excluding transfers, pending rows and zero amounts; refunds and income therefore never pollute a charge series. Each of 8 cadences (weekly, biweekly, twice_monthly, monthly, bimonthly [addition], quarterly, semiannual, yearly) is fitted from the data (median day-of-month with end-of-month normalisation; two anchor days for twice-monthly; relative 7/14-day steps for week-based) and scored by walking the sorted dates: hit / skip (one period missed, half credit) / extra (second charge in the same period, cursor does not advance) / miss. Score is integer basis points ((2·hits+skips)·10000)/(2·(n−1)); accept iff ≥ 6000, hits ≥ 2, on-cycle ≥ 3, n ≥ 3 (n ≥ 4 for variable amounts and for twice-monthly), amounts not dispersed beyond ×2 of the median, last charge not stale (≤ 2 periods old). If the whole payee group fails, the per-account split is tried, then amount clusters (two Spotify accounts; iCloud + Music under one Apple payee). Amounts: fixed iff the last 3 charges lie within max(100¢, 1%) → expected = last charge, tolerance = max(100¢, 1%); otherwise variable → expected = upper median of the last 6, tolerance = band half-width covering them. Persistence: `recurring` rows (status suggested/active/paused/cancelled/dismissed, lock flags for user edits, denormalised last/next/missed fields that are pure functions of links + locks + today), `transaction.recurring_id` links (series identity across re-runs = link overlap, which is what keeps dismissals sticky and edits safe), and an `alert` table with a unique dedupe_key so re-runs and retries never duplicate alerts. Next due = first occurrence after the last charge's period whose grace has not elapsed (anchor 31 = last day of month, clamped). Subscriptions page: yearly = expected × {52,26,24,12,6,4,2,1}, monthly-equivalent = yearly/12 rounded half away from zero in bigint, totals from the exact yearly sum. Four alerts: price_increase (fixed items, |new|−|last| > tolerance), new_recurring (suggestion whose first charge is within 120 days of today and ≥ 45 days after that account's history start), missed_charge (per occurrence, grace 2/3/4/5/5/7/10/14 days by cadence, auto-pause after 3 consecutive), trial_converted (first charge ≥ $5 within 45 days after only ≤ $1 charges, raised within 14 days). 27 hand-verified test cases follow (every number re-computed by me with a throwaway implementation of this exact algorithm).

## algorithm

All dates are IsoDate strings (UTC calendar, packages/shared/src/dates.ts: dayDiff, addDays, dayOfMonth). All money is bigint cents; `/` on bigint truncates toward zero (for the non-negative operands used here that is floor). Day counts, indices and basis points are plain integers (never money). No float ever touches a cent.

### A. Schedule primitives — packages/shared/src/schedule.ts (new)
```ts
type Cadence = 'weekly'|'biweekly'|'twice_monthly'|'monthly'|'bimonthly'|'quarterly'|'semiannual'|'yearly';
interface Schedule { cadence: Cadence; anchorDate?: IsoDate; anchorDay?: number; anchorDay2?: number; anchorMonth?: number }
function daysInMonth(y: number, m: number): number
function isLastDayOfMonth(d: IsoDate): boolean
function effectiveDay(d: IsoDate): number        // 31 when d is the last day of its month, else dayOfMonth(d)
function monthIndex(d: IsoDate): number          // y*12 + (m-1)
function periodMonths(c: Cadence): 0|1|2|3|6|12
function occurrence(s: Schedule, k: number): IsoDate
function periodIndex(s: Schedule, d: IsoDate): { k: number; residualDays: number }   // residual = dayDiff(occurrence(k), d), signed
function occurrencesInRange(s: Schedule, from: IsoDate, to: IsoDate): IsoDate[]     // inclusive; the bills/income auto-fill and cash-flow areas import this
function toleranceDays(c), graceDays(c), nominalPeriodDays(c), occurrencesPerYear(c): bigint
function isMissed(due: IsoDate, today: IsoDate, c: Cadence): boolean   // dayDiff(due, today) > graceDays(c)
```
occurrence(s, k):
- weekly/biweekly: addDays(anchorDate, k·P), P = 7 | 14.
- monthly/bimonthly/quarterly/semiannual/yearly: M = base + k·periodMonths where base = 0 for monthly else anchorMonth−1; y = floor(M/12), m = (M mod 12)+1; day = min(anchorDay, daysInMonth(y, m)). anchorDay 31 therefore yields Feb 28/29, Apr 30, etc.
- twice_monthly: M = floor(k/2), slot = k mod 2; y, m from M; day = min(slot === 0 ? anchorDay : anchorDay2, daysInMonth(y, m)).
periodIndex(s, d):
- week-based: diff = dayDiff(anchorDate, d); k = Math.floor((2·diff + P) / (2·P)) (round half up, works for negative diff); residual = diff − k·P.
- month-based: k0 = floor((monthIndex(d) − base) / periodMonths); evaluate k0−1, k0, k0+1; pick the smallest |dayDiff(occurrence(k), d)|, ties → smaller k. (This puts "posted Jun 1 for the May 31 bill" in May and "posted Jan 30 for the Feb 1 bill" in Feb.)
- twice_monthly: candidates k ∈ {2(M−1), 2(M−1)+1, 2M, 2M+1, 2(M+1), 2(M+1)+1} with M = monthIndex(d); nearest, ties → smaller k.
occurrencesInRange(s, from, to): start at k = periodIndex(s, from).k − 2 and step k upward, collecting occurrence(k) ∈ [from, to], stopping at the first occurrence > to.

### B. Detection — packages/shared/src/recurringDetect.ts (pure, no DB)
```ts
interface ChargeLike { id: string; accountId: string; date: IsoDate; amountCents: bigint }
interface CadenceScore { cadence: Cadence; schedule: Schedule; n: number; hits: number; skips: number; extras: number; misses: number; onCycle: number; scoreBp: number; residualSum: number; onCycleIds: string[]; firstOnCycle: boolean }
interface Detection { schedule: Schedule; scoreBp: number; confidence: number; amountMode: 'fixed'|'variable'; expectedCents: bigint; toleranceCents: bigint; onCycleIds: string[]; firstChargeDate: IsoDate; lastChargeDate: IsoDate; lastChargeCents: bigint; lastTransactionId: string; accountId: string; chargeCount: number; nextDueDate: IsoDate }
function upperMedian<T extends bigint|number>(xs: T[]): T          // sorted[floor(n/2)]
function fitSchedule(dates: IsoDate[], cadence: Cadence): Schedule | undefined
function scoreCadence(dates: IsoDate[], ids: string[], schedule: Schedule): CadenceScore
function classifyAmounts(absAmounts: bigint[] /* chronological */): { mode: 'fixed'|'variable'; expectedAbs: bigint; toleranceCents: bigint; dispersed: boolean }
function compareScores(a: CadenceScore, b: CadenceScore): number
function detectSeries(charges: ChargeLike[], today: IsoDate): Detection | undefined
function clusterByAmount(charges: ChargeLike[]): ChargeLike[][]
function detectRecurring(group: ChargeLike[], today: IsoDate): Detection[]     // whole → per account → amount clusters
function isNewSeries(firstChargeDate: IsoDate, accountHistoryStart: IsoDate, today: IsoDate): boolean
function detectTrialConversion(outflows: ChargeLike[], today: IsoDate): { smallTransactionIds: string[]; firstFull: ChargeLike } | undefined
function divRound(n: bigint, d: bigint): bigint      // d > 0; half away from zero: q = (2·|n| + d) / (2·d), sign restored
function yearlyCents(expectedCents: bigint, c: Cadence): bigint               // expectedCents * occurrencesPerYear(c)
function monthlyEquivalentCents(expectedCents: bigint, c: Cadence): bigint    // divRound(yearlyCents(...), 12n)
```
B1. Grouping (service side, C1): a group = all transactions with the same payee_id and the same sign of amount_cents, with is_transfer = false, pending = false, amount_cents ≠ 0, date ≥ addMonths(today, −36) and date ≤ today; sorted by (date, id). Refunds (opposite sign) are a different group and never pollute a series.

B2. fitSchedule(dates, cadence):
- weekly/biweekly: { anchorDate: dates[0] } (the walk re-anchors at each on-cycle charge; this only starts it).
- monthly/bimonthly/quarterly/semiannual/yearly: anchorDay = upperMedian(effectiveDay(d) for all dates). For periodMonths p > 1: residue r(d) = monthIndex(d) mod p; take the residue class with the most charges (tie → the class of the earliest charge); anchorMonth = calendar month (1..12) of the earliest charge in that class.
- twice_monthly: requires n ≥ 4, else undefined. s = effective days sorted ascending; for each contiguous split i in 1..n−1: cost(i) = Σ|x − upperMedian(lo)| + Σ|x − upperMedian(hi)|; pick the minimum cost (tie → smaller i). anchorDay = upperMedian(lo), anchorDay2 = upperMedian(hi). Valid iff |lo| ≥ 2, |hi| ≥ 2 and min(B−A, 30−(B−A)) ≥ 10; otherwise undefined (so (1,31) and (3,5) are rejected).

B3. scoreCadence (the walk). tol = toleranceDays(cadence). cursor = dates[0]. Week-based: kCur = 0, firstOnCycle = true. Otherwise {k, r} = periodIndex(schedule, dates[0]); kCur = k; firstOnCycle = |r| ≤ tol. For each later charge c (i = 1..n−1):
 - week-based: diff = dayDiff(cursor, c); dk = floor((2·diff + P)/(2·P)); r = diff − dk·P; k = kCur + dk.
 - month-based / twice-monthly: {k, r} = periodIndex(schedule, c); dk = k − kCur.
 classify: dk = 0 → extra (counters only; cursor and kCur unchanged); else |r| > tol → miss (cursor = c, kCur = k); else dk = 1 → hit; dk = 2 → skip; dk ≥ 3 → miss. On hit/skip/miss the cursor advances to c (so for week-based the next prediction is from the actual charge and jitter never accumulates). hits/skips add |r| to residualSum and their ids to onCycleIds (dates[0] is included iff firstOnCycle). onCycle = (firstOnCycle ? 1 : 0) + hits + skips. scoreBp = floor(((2·hits + skips)·10000) / (2·(n−1))); extras and misses earn nothing but stay in the denominator.

B4. Accept a CadenceScore iff scoreBp ≥ 6000 AND hits ≥ 2 AND onCycle ≥ 3 (twice_monthly additionally n ≥ 4 and both anchor clusters ≥ 2, enforced by fitSchedule).

B5. compareScores (best first): higher scoreBp; tie → smaller tolerance-normalised residual compared without division: a wins iff residualSum_a · tol_b · gaps_b < residualSum_b · tol_a · gaps_a (gaps = n−1); tie → longer nominalPeriodDays (plans fewer occurrences).

B6. classifyAmounts(abs amounts, chronological): last3 = last min(3, n); mFixed = upperMedian(last3); tolFixed = max(100n, mFixed / 100n). fixed iff max(last3) − min(last3) ≤ tolFixed → expectedAbs = last amount (a price change is reflected immediately), toleranceCents = max(100n, expectedAbs / 100n). Else variable: last6 = last min(6, n); expectedAbs = upperMedian(last6); toleranceCents = max(expectedAbs − min(last6), max(last6) − expectedAbs). dispersed = any amount a in the whole series with 2·a < upperMedian(all) or a > 2·upperMedian(all) (bimodal guard).

B7. detectSeries(charges, today): n < 3 → undefined. amounts = classifyAmounts. If variable and n < 4 → undefined (three roughly monthly purchases at three prices are not a bill). If variable and dispersed → undefined (handed to clustering by B8). For each cadence: fitSchedule → (undefined → skip) → scoreCadence → B4; pick the best by B5; none → undefined. Stale guard: lastOnCycle = date of the last onCycleId; dayDiff(lastOnCycle, today) > 2·nominalPeriodDays → undefined. Build Detection: expectedCents = sign·expectedAbs; nextDueDate = week-based ? addDays(lastOnCycle, P) : occurrence(schedule, periodIndex(schedule, lastOnCycle).k + 1) (week-based schedules store anchorDate = lastOnCycle); accountId = account of the last on-cycle charge; first/lastChargeDate from on-cycle charges; lastChargeCents/lastTransactionId from the last on-cycle charge; chargeCount = onCycleIds.length; confidence = floor(scoreBp / 100). Only on-cycle ids are linked; extras and misses stay unlinked.

B8. detectRecurring(group, today): (1) d = detectSeries(group) → [d] if defined. (2) else if the group spans ≥ 2 accounts: detectSeries per account → every defined result. (3) if still nothing: clusterByAmount: sort by |amount|; greedy clusters where a ≤ clusterMin + max(100n, clusterMin·15n/100n) (clusterMin = smallest amount in the current cluster); clusters with ≥ 3 charges → detectSeries each → every defined result. Levels are never combined. Output ordered by chargeCount desc, firstChargeDate asc, then first onCycleId asc (deterministic).

B9. isNewSeries(first, historyStart, today) = dayDiff(first, today) ≤ 120 AND dayDiff(historyStart, first) ≥ 45, where historyStart = the earliest transaction date in the account of the first on-cycle charge (so a first 93-day sync does not flag every bill, and a yearly item detected after three years is never "new").

B10. detectTrialConversion(all outflows of one payee including zero and small amounts, sorted by date, 36-month window): i = index of the first charge with |a| ≥ 500n; fire iff i ≥ 1, every earlier charge has |a| ≤ 100n, dayDiff(date[i−1], date[i]) ≤ 45 and dayDiff(date[i], today) ≤ 14. Returns the small ids and the full charge.

B11. Subscriptions math: yearlyCents = expectedCents × occurrencesPerYear (52/26/24/12/6/4/2/1; weekly×52 and biweekly×26 ignore the 53rd/27th charge some years have; documented). monthlyEquivalentCents = divRound(yearlyCents, 12n). Page totals: totalYearlyCents = Σ yearlyCents (exact); totalMonthlyCents = divRound(totalYearlyCents, 12n), never a sum of rounded rows.

### C. Persistence — packages/db/src/services/recurring.ts
```ts
loadDetectionInput(db, today): Promise<{ groups: Map<string /* payeeId|sign */, ChargeLike[]>; historyStartByAccount: Map<string, IsoDate> }>
runRecurringDetection(db, opts: { today: IsoDate; now: Date }): Promise<{ groups: number; suggestionsCreated: number; suggestionsUpdated: number; suggestionsDeleted: number; groupsSkipped: number; itemsMatched: number; alertsCreated: number }>
upsertDetections(tx, payeeId: string, sign: 1n|-1n, detections: Detection[], existing: RecurringRowWithLinks[], runStart: Date, today: IsoDate, historyStartByAccount): Promise<void>
matchRecurringItems(tx, today: IsoDate, now: Date, opts?: { ids?: string[] }): Promise<number>
refreshRecurringItem(tx, id: string, today: IsoDate, now: Date, opts?: { newlyLinkedIds?: string[] }): Promise<void>
raiseAlert(tx, alert: { kind: AlertKind; dedupeKey: string; recurringId?: string; payeeId: string; transactionId?: string; dueDate?: IsoDate; oldCents?: bigint; newCents?: bigint }): Promise<boolean>   // insert on conflict (dedupe_key) do nothing → false when it existed
listSubscriptions(db): Promise<{ items: SubscriptionRow[]; pausedItems: SubscriptionRow[]; totalMonthlyCents: bigint; totalYearlyCents: bigint }>
```
C1. Detector run (one DB transaction; the job is deduped so only one runs at a time). runStart = now. For each group: detections = detectRecurring(group, today) wrapped in try/catch (an engine error logs the payee, counts groupsSkipped and leaves that payee's rows untouched, including their detected_at, so they are not cleaned up as stale). existing = recurring rows with this payee_id and sign(expected_cents) = sign, each with its set of linked transaction ids. Identity mapping: for each detection in B8 order, candidate rows not yet claimed in this run with |onCycleIds ∩ links(row)| ≥ 1; take the largest overlap (tie → oldest created_at).
 - mapped row with status 'suggested' → update cadence/anchors/expected/tolerance/amount_mode/confidence/first/last/next_due/account_id/charge_count/last_transaction_id, category_id (modal category of the on-cycle charges, else payee.default_category_id, else unchanged), detected_at = runStart; relink: set recurring_id = row.id on onCycleIds, null on previously linked ids not in onCycleIds.
 - mapped row with any other status → set detected_at = runStart only. Parameters and links belong to the user and the matcher.
 - no row → insert a suggested row (source 'detected', name = payee name, category as above) + link onCycleIds + if expectedCents < 0 and isNewSeries(firstChargeDate, historyStart(accountId), today) → raiseAlert(new_recurring, 'new:<id>').
 After all groups: delete recurring rows where status = 'suggested' and source = 'detected' and payee_id not in skipped groups and (detected_at is null or detected_at < runStart) — not reproduced (stale, merged, re-categorised). The FK nulls their links and cascades their alerts. Then matchRecurringItems() for every row with status in (active, paused, dismissed) and trial detection per outflow payee group (raiseAlert 'trial:<payeeId>:<txId>', payee_id set, recurring_id null).
C2. Matcher (status active, paused, dismissed; suggested rows are owned by the detector; cancelled rows never match). Candidates = transactions with payee_id = item.payee_id, recurring_id is null, is_transfer = false, amount_cents ≠ 0, sign(amount) = sign(expected), pending included (a bill shows as paid as soon as it is pending), date > last_charge_date (or date ≥ addDays(missed_from_date, −nominalPeriodDays) when the item has no charge). If another row of the same payee and sign with status in (active, paused) has a different account_id, restrict candidates to item.account_id (two Spotify accounts); otherwise any account (a card move follows). Amount gate: fixed → expected/2 ≤ |a| ≤ 2·expected (as 2·|a| ≥ |expected| and |a| ≤ 2·|expected|); variable → 3·|a| ≥ |expected| and |a| ≤ 3·|expected|. For each candidate in date order: {k, r} = periodIndex; require k > kLast (kLast = periodIndex(last_charge_date).k, or −∞ with no charge) and no linked charge in period k; link iff |r| ≤ graceDays(cadence) OR | |a| − |expected| | ≤ tolerance_cents (an on-amount charge re-anchors a bill whose billing day moved); if several candidates share a period keep the smallest |r| (tie → earlier date, then smaller id). Then refreshRecurringItem(id, today, now, { newlyLinkedIds }).
C3. refreshRecurringItem (derived state, idempotent): links sorted by (date, id). first/last_charge_date, last_charge_cents, last_transaction_id, charge_count, account_id = account of the last link (unless no links: leave). Unless amount_locked: classifyAmounts over the linked absolute amounts → expected_cents (signed), tolerance_cents, amount_mode. Unless schedule_locked: month-based anchor_day = upperMedian(effectiveDay of the last ≤ 6 links); twice-monthly anchors re-fit (B2) on the last ≤ 12 links (keep the old anchors if the fit is undefined); week-based anchor_date = last link date; anchor_month unchanged. kLast = periodIndex(last_charge_date).k (no charge: kLast = periodIndex(addDays(missed_from_date, −1)).k). Missed evaluation (status active only): for k = kLast+1, kLast+2, … while occurrence(k) ≥ missed_from_date and isMissed(occurrence(k), today, cadence): raiseAlert(missed_charge, 'missed:<id>:<occurrence>', due_date = occurrence(k)); consecutive_missed = that count; next_due_date = occurrence(first k not missed). For status paused/dismissed: consecutive_missed = 0 and next_due_date = occurrence(kLast+1) advanced past occurrences < today. If consecutive_missed ≥ 3 and status = 'active' → status 'paused', status_reason 'missed_3', status_changed_at = now. Price increase (status active, amount_mode fixed before this refresh, for each newly linked charge c in date order against the previous last_charge_cents L): if |c| − |L| > tolerance_cents (the value before refresh) → raiseAlert(price_increase, 'price:<id>:<c.id>', old_cents = L, new_cents = c). A newly linked charge whose period k has an open missed_charge alert (due_date = occurrence(k)) sets that alert's resolved_at = now. Variable items never raise price_increase.
C4. Status transitions (API): suggested→active (requires category_id; sets missed_from_date = last_charge_date ?? today, resolves its new_recurring alert, sets payee.default_category_id = category_id when the payee has none, then refresh); suggested→dismissed (resolves its new_recurring alert; links are kept so the series keeps mapping to this row and is never re-suggested while it continues); active↔paused (resume sets missed_from_date = today, consecutive_missed = 0, status_reason null); active|paused→cancelled (next_due_date null); cancelled|dismissed→active (as confirm: missed_from_date = today, then refresh). Any other transition is 400 'invalid_transition'. Manual create: source 'manual', status 'active', schedule from the body, amount_locked = schedule_locked = true, missed_from_date = today, then matchRecurringItems({ ids: [id] }). Editing expected/tolerance/amountMode sets amount_locked; editing cadence/anchors sets schedule_locked and recomputes next_due_date synchronously via refresh.
C5. Ledger hooks: updateTransaction with a payee change, isTransfer = true, or amount sign change sets recurring_id = null and calls refreshRecurringItem on the old item; rows deleted by sync (vanished pending) drop their link via the FK; createManualTransaction and a CSV commit enqueue 'recurring.detect' { reason: 'ledger' } (dedupe: true).
C6. Worker: apps/worker/src/jobs/recurringDetect.ts exports runRecurringDetectJob(ctx, job) → runRecurringDetection(ctx.db, { today: toIsoDate(ctx.now()), now: ctx.now() }); apps/worker/src/jobs/index.ts dispatches 'recurring.detect'. Enqueued (dedupe: true) at the end of a successful simplefin.sync that is not balances-only ({ reason: 'sync' }), by POST /recurring/detect ({ reason: 'manual' }), by the API hooks in C5, and by scheduler.ts once per UTC day: on each tick, if ctx.now().getUTCHours() ≥ config.detectHourUtc (default 8) and no 'recurring.detect' job has created_at ≥ today's 00:00 UTC, enqueue { reason: 'nightly' }.

## edgeCases

- Refund mixed into a series: sign splits the group, so +1549 from Netflix is a separate 1-charge group that is neither linked nor counted; a payroll reversal likewise never touches the inflow series.
- Same payee on two accounts, one subscription that moved cards (6 charges on A then 4 on B): the whole-group walk passes (gaps still monthly) → one item; account_id follows the latest charge so the cash-flow projection debits the new card.
- Same payee on two accounts, two distinct subscriptions (two Spotify): the whole-group walk sees an extra every period → 4285 bp rejected → per-account split → two items; the matcher restricts each to its own account because another live item of the same payee has a different account_id.
- One payee with several subscriptions at different prices (Apple: iCloud 299 + Music 1099 + a one-off 499): the whole group fails the ×2-of-median dispersion guard, the per-account split is identical, amount clustering (15% band above the cluster minimum) yields two monthly items; the 499 one-off is a 1-charge cluster and is ignored.
- A one-off purchase from a subscription payee (Netflix + an off-cycle charge): the extra does not move the cursor, score 8000 still passes, only on-cycle charges are linked; the amount gate in the matcher (fixed: 0.5×..2×) keeps a $200 modem from the $80 ISP from being linked or raising a false price alert.
- Bill on the 31st: effectiveDay maps the last day of any month to 31, so the anchor is 31 even though Feb 28 / Apr 30 / Jun 30 posted; occurrence() clamps to the month length; a charge posted Jun 1 for the May 31 bill lands in May's period by nearest-occurrence assignment (residual +1).
- Bill genuinely on the 28th: the single Feb 28 charge contributes 31, but the upper median of {28,28,28,31} is 28, so EOM normalisation does not disturb it.
- Weekday-only posting (due the 5th, posted the 6th/7th on weekends): monthly tolerance ±4 covers Sat/Sun/holiday shifts; the anchor is the median of effective days so it does not random-walk forward.
- Twice-monthly vs biweekly: gaps alone cannot separate them (1st/15th gives gaps 13..17); the twice-monthly model with two fitted anchors scores 10000 vs biweekly 8000 for a 1st/15th payroll, and a true every-other-Friday payroll scores 10000 biweekly vs 8333 twice-monthly; the tie-break (normalised residual, then longer period) is only reached on exact ties.
- Three random dates can always be fitted by two free twice-monthly anchors, hence twice-monthly needs n ≥ 4 and ≥ 2 charges per anchor, and month-based cadences require the first charge to be on-cycle too (onCycle ≥ 3).
- Three roughly monthly charges with three different prices look like a bill by dates alone; variable-amount series need ≥ 4 charges; fixed ones need 3.
- Early paycheck around a month boundary (the 1st posting on Jul 31): nearest-occurrence assignment puts Jul 31 in Aug-A with residual −1.
- Price increase: fixed items follow the last charge (expected := new) and alert when |new| − |last| > tolerance (max(100¢, 1%)); a 50¢ change does not alert; a one-off discounted month lowers next month's plan until the next charge (documented; the user can lock the amount).
- Variable bills (utilities) never raise price_increase alerts because seasonal swings are expected; their tolerance is the band over the last 6 charges and is recomputed after every match unless amount_locked.
- A confirmed bill whose billing day moves (5th → 20th): the matcher links by amount when the period is free even though the residual exceeds grace; the anchor median follows after three charges; a variable bill with a moved date needs the user to edit the anchor (schedule_locked).
- Missed-charge boundary: due Oct 5, grace 5 → not missed on Oct 10 (dayDiff 5), missed on Oct 11 (6 > 5); the alert is keyed by due date so re-runs never duplicate it; a late charge on Oct 12 links to October, resets consecutive_missed to 0 and resolves the alert.
- Three consecutive missed occurrences auto-pause an active item (status_reason 'missed_3') so the bills bucket stops planning a dead subscription; resume restarts the missed clock from today so it is not re-paused immediately.
- Pending charges are excluded from detection (dates/amounts unstable) but linked by the matcher, so a pending Netflix charge on the due date prevents a missed alert; when it posts, Phase 1 keeps the row id and the link survives; a vanished pending row drops its link via FK.
- Zero-amount transactions are excluded from series detection but included in trial detection (a $0 authorization followed by a $17.99 charge within 45 days is a converted trial); a full charge that precedes the small one is not a trial; a $1.50 'full' charge is below the $5 floor and is not a trial.
- New-subscription alert on a first sync: with 93 days of history every monthly bill's first charge is within 120 days, so the 45-day history guard (first charge ≥ 45 days after the account's earliest transaction) suppresses them; after a CSV history import the same guard applies against the imported start.
- Yearly/semiannual items are never 'new' (three charges cannot fit in 120 days); a yearly series detected from a 3-year import is correctly not announced.
- Stale series (gym cancelled 100 days ago, monthly): 100 > 62 → not suggested, and an existing suggested row is deleted on the next full run; active items are never auto-deleted (missed logic handles them).
- Dismissed suggestions keep their links; because series identity is link overlap, the series maps to the dismissed row on every re-run and is never re-suggested while it continues; if it stops for longer than the lookback and restarts, it is a new series and is suggested again (state this in the UI).
- Re-run after a sync: an existing suggestion is updated in place (same id, charge_count 5 → 6, next_due advanced) because the new series overlaps its links; two old suggestions that merge into one series leave one unreproduced and it is deleted; a series that splits claims the row with the larger overlap and inserts one new row.
- Payee merge (PATCH /payees/:id mergeFromId moves transactions and aliases the name): recurring.payee_id and alert.payee_id must be re-pointed in the same transaction, else the FK cascade deletes the items and alerts.
- Yearly items need 3 charges = at least 25 months of history, so the 36-month lookback and the history CSV import matter; with only the 93-day initial SimpleFIN window, weekly/biweekly/twice-monthly/monthly appear first and quarterly after ~6 months.
- Bimonthly (water/trash) is not one of the spec's seven cadences; under monthly it scores 5000 (all skips) and under quarterly 3333, both rejected, so it is added as an eighth cadence; every-4-weeks charges (some gyms) remain undetected (documented gap).
- Two identical charges on the same day every month (two Netflix profiles): every level sees an extra each period and fails; not detected (documented).
- Leap day: anchor 31 clamps to Feb 29 in leap years and an anchor of 29 clamps to Feb 28 otherwise; dayDiff is UTC-based so DST never yields 23/25-hour days.
- Retried or half-finished job: every alert insert is on conflict do nothing and every denormalised field is recomputed from links, so a crash mid-run followed by a full run converges to the same state; a group whose detection throws is skipped and its suggestions are not deleted as stale.
- Monthly-equivalent rounding: half away from zero in bigint (−54/12 → −5, +54/12 → +5, −50/12 → −4); page totals come from the yearly sum so the monthly total is not the sum of rounded rows.
- Weekly item due today (next_due_date = today): not overdue (dayDiff 0 ≤ grace 2); a run three days later without a charge raises missed_charge for today's date and advances next_due by 7 days.
- Manual item whose payee never matches a transaction (bank uses a different name): it accumulates missed alerts every period and auto-pauses after three, which is the signal to add a payee alias; nothing silently 'pays' it.

## risks

- Minimum of 3 charges with ±4-day monthly tolerance will occasionally suggest a false bill for a frequently used merchant whose same-priced purchases land ~monthly, and 4 variable charges 28–34 days apart (Amazon-like) are accepted as a variable monthly item (verified: anchorDay 3, 10000 bp). Mitigations: the fixed-amount rule for n = 3, the ×2 dispersion guard, one-click sticky dismiss. First-run suggestion lists may be long on noisy accounts; if that bites, raise MIN_CHARGES_VARIABLE to 5 (one constant).
- Yearly (and semiannual) detection needs ≥ 25 months of history; the spec's '12+ months' cannot deliver it. The 36-month lookback only helps once the history CSV import (spec open question) exists; until then yearly items are entered manually.
- Series identity by link overlap means a dismissed suggestion stays dismissed only while its charges keep arriving; a series that stops for longer than the lookback and restarts is re-suggested. Intended, but the UI should say so.
- Auto-pausing after three consecutive missed charges changes a user-visible status without the user acting; it protects the bills bucket from phantom bills, but an item that stopped posting for an innocent reason (payee rename, bank outage) is paused. The alert explains it and resume is one click; the lead should confirm.
- Fixed items follow the last charge immediately (expected := last); a one-off promo or partial month lowers next month's planned amount until the next charge, which then raises a price_increase alert. Chosen for immediacy (the plan should show the new price); the amount lock is the escape hatch.
- Amount clustering can produce odd sub-series for high-volume payees when a few same-priced purchases align monthly; it only runs after the whole group and the per-account split fail, and suggestions are reviewable, but it is the most speculative part and could be behind a constant (CLUSTER_ENABLED).
- Payee normalisation quality bounds detection: raw descriptions with varying store numbers that Phase 1 fails to collapse split a series into sub-threshold groups; aliases and merges fix this, and the merge route must re-point recurring.payee_id and alert.payee_id (new requirement on existing Phase 1 code).
- Two subscriptions of the same payee, same amount, same account, same day (two Netflix profiles) are undetectable; 'every 4 weeks' billing drifts out of the monthly anchor and is not a cadence — both are documented gaps, not silent errors.
- 'bimonthly' is an eighth cadence beyond the spec's seven; it costs nothing in the generic period machinery but appears in the bills auto-fill and the cash-flow engine enums, so the other Phase 2 areas must include it.
- The bills/income bucket must enumerate occurrencesInRange(month) per active item rather than read next_due_date; using next_due_date would drop quarterly items whose next due lies in a later month, under-count twice-monthly income, and lose a late bill whose next_due advanced past its month. This is a hard constraint on the plan-math area.
- Calendar dates are UTC (Phase 1 convention); a charge posted late evening local time can land on the next UTC day, which the tolerances absorb but which can make 'due on the 1st' read as 'due on the 2nd'.
- Alert idempotency depends on dedupe_key; if a transaction is deleted and re-imported under a new id (CSV re-import after an edit), price/trial alerts keyed by transaction id can be raised again. Keying by (recurring_id, period) would avoid that but miss a genuine second increase in the same period; transaction id is kept.
- Denormalised fields (next_due_date, consecutive_missed, last charge) are refreshed by the job (after sync, nightly, 'Scan now', and after manual/CSV ledger writes). A transaction edited by hand is reflected in the item after the next run, not instantly, except for the C5 hooks.
- The reports area's 'subscription cost per year and its trend' needs history; this design provides status_changed_at and price_increase alerts (old/new cents) as the raw material but does not keep a per-month snapshot of subscription totals. If the trend chart needs exactness, add a monthly snapshot job in the reports area.

## resolutions

- Scoring model: Design A's calendar-aware walk (hit/skip/extra/miss, integer basis points) over Design B's consecutive-gap fit ratio. Reason: B's gap test turns one duplicate charge into two bad gaps (its own T9 drops to 5/7 and needs a 0.70 threshold to survive) and cannot represent 'extra' charges; A's walk scores the same series 8571 with the duplicate correctly unlinked, handles end-of-month clamping and skipped periods, and its anchors come from medians rather than from the previous charge, so jitter never accumulates.
- Cadence set: the spec's seven plus 'bimonthly' (A's addition), named 'twice_monthly' for the spec's 'twice monthly' (B used 'semimonthly'). Reason: a bimonthly bill is verified to score 5000 under monthly and 3333 under quarterly, both rejected, and the generic periodMonths machinery makes the eighth cadence free; the other Phase 2 areas must carry it in their enums.
- Minimum charges: 3 for fixed amounts, 4 for variable amounts and for twice-monthly (A) rather than a flat 3 (B). Reason: three roughly monthly purchases at three prices (TC6) are the canonical false positive and B's own T8 only rejects it because the dates happen not to fit; two free twice-monthly anchors can fit any three dates.
- Minimum confidence: scoreBp ≥ 6000 with hits ≥ 2 and onCycle ≥ 3 (A). B's fit ≥ 0.70 is defined on a different statistic and does not transfer; under A's scoring 6000 admits one duplicate or one skip in short series while rejecting all-skip (5000) patterns.
- Expected amount: fixed → last charge, variable → upper median of the last 6 (A), instead of B's lower median of the last 3 for everything. Reason: the spec alerts on price increases 'versus the last charge' and the bills bucket should plan the new price immediately rather than two charges later; the amount lock covers promo months. Fixed band = max($1, 1%) (A) rather than 2% (B): a 2% band on a $245,000-cent paycheck is $49, too loose for 'fixed'.
- Price-increase rule: fixed items only, |new| − |last| > tolerance_cents (A); B's extra '5% or $1' and 'exceeds band' conditions are dropped because the matcher's amount gate (0.5×–2× for fixed) already keeps the $200 modem from the $80 ISP out of the series, which was the false alert B's rule was guarding against. Variable items never alert (both designs effectively agree; B's rule would only fire outside the band, which the gate also blocks).
- Series identity and persistence: transaction.recurring_id link column with identity-by-link-overlap (A) rather than B's (payee, sign) key and tombstone. Reason: B's key cannot represent two series under one payee (two Spotify accounts, Apple iCloud + Music), which the lead explicitly asked about; and the spec's pipeline step 'match recurring' and the drill-down need the link anyway. B's 'suggestions keyed by (payee, sign) never duplicate' property is preserved because overlap mapping updates the existing row in place.
- User edits: amount_locked / schedule_locked flags (A) instead of flipping source to 'manual' (B). Reason: B itself flagged the loss of provenance; two booleans keep source truthful and let the matcher keep refreshing the unlocked half.
- Grouping fallbacks: whole group → per account → amount clusters (A). B documented two-series-per-payee as a limitation; the lead asked for the two-account case to be handled, so A's cascade stays, with clustering last and only after the first two levels fail.
- Next due date and missed charges: A's per-occurrence iteration from the last charge's period, grace per cadence 2/3/4/5/5/7/10/14, one alert per missed occurrence, auto-pause after three (A), rather than B's 'latest missed date per run' and grace = tolerance + 1. Reason: B's single-alert-per-run misses occurrences when the job does not run for a while and B's yearly grace of 8 days is too tight for renewals; A's grace table keeps grace > tolerance in every row, which was B's invariant.
- New-subscription alert: B's definition (first charge within 120 days of today AND at least 45 days after that account's earliest transaction), replacing A's 'within 3·period + 14 days'. Reason: my re-computation shows A's rule flags every yearly and semiannual series as new (TC5: 943 ≤ 1112 days) and would flag every monthly bill on a first 93-day sync; B's history guard fixes both and a flat 120-day window makes long cadences never 'new', which is correct.
- Trial conversion: merged rule — full charge ≥ 500¢ (B's floor), all earlier charges ≤ 100¢ (A, includes $0), within 45 days of the last small charge and raised only within 14 days of the full charge (A). Reason: A's >$1 threshold would call a $1.50 charge a conversion; B's 'latest charge' formulation re-evaluates forever, while A's recency guard keeps a history import from flooding old conversions.
- Lookback: 36 months (A) vs 1100 days (B): equivalent intent; months are used because the window is defined in calendar terms like everything else here. Both designs agree the spec's '12+ months' cannot yield yearly items; recorded as a risk.
- Pending transactions: excluded from detection but linked by the matcher (A), not counted as charges (B). Reason: pending dates and amounts move, which would perturb anchors and amount stats; linking them lets a bill show as paid before it posts.
- Alert table: a generic `alert` table (A) rather than `recurring_alert` (B); later phases may add other kinds. dedupe_key formats from A; B's auto-dismiss on confirm/dismiss/late charge is kept as resolved_at (distinct from the user's dismissed_at so the UI can tell them apart).
- Subscriptions totals: totalMonthly = divRound(Σ yearly, 12) (A), not the sum of rounded rows (B). Reason: CLAUDE.md's integer-math rule wants one documented rounding, and a sum of rounded rows drifts by up to one cent per row.
- Nightly run: scheduler enqueues once per UTC day after DETECT_HOUR_UTC (A) rather than '24 h since the last finished run' (B). Reason: deterministic time of day and no dependence on finished_at of a possibly failed run; both avoid a cron table.
- Run transaction scope: one transaction for the whole run (A) with B's concern addressed differently: a group whose pure detection throws is caught, logged, counted, and excluded from stale cleanup, so one bad payee neither fails the run nor deletes its own suggestions.
- Added because both designs left it implicit or missing: (1) the existing PATCH /payees/:id merge must re-point recurring.payee_id and alert.payee_id in the same transaction (both listed it as a risk; it is now a requirement); (2) createManualTransaction and CSV commits enqueue recurring.detect so the spec's 'match recurring' pipeline step runs for every ingest path, not only SimpleFIN sync; (3) a computed `overdue` field in RecurringView (B had it; A did not) so the UI needs no date math; (4) pausedItems on the Subscriptions response so auto-paused subscriptions are visible but outside the totals; (5) PATCH confirm sets payee.default_category_id when empty (B) so future charges are categorized by Phase 1 ingest.
- Test cases: all 22 of A's cases were re-computed and kept with corrections (TC1/TC4 'other cadences score 0' claims replaced by actual scores; TC5 and TC18 'isNew' expectations rewritten under the new rule; TC8 corrected: after a 1549→1799 jump the last-3 spread makes the item temporarily variable with expected 1549 and tolerance 250, not 'expected −1799' as A wrote); B's T6 (quarterly variable), T13 (semiannual), T14 (weekly due today), T9 (duplicate charge) and T16 (card move) were re-computed under the merged algorithm and added as TC23, TC24, TC25, TC20 and TC27; TC26 was added for the history guard. B's T2/T4/T5 were verified to behave as expected under the merged engine (monthly 10000 with expected −13380/tolerance 4740; twice-monthly 10000 vs biweekly 8333; biweekly 10000 with residualSum 2) and are covered by TC2/TC3/TC9.
