# Phase 3 seams: conflicts, gaps and build order

Seam critic's report over the four merged area designs in this directory (`imports-and-data.md`, `lots-and-performance.md`, `prices-and-valuation.md`, `views-and-api.md`), read against the design spec's Phase 3 scope and gate, `docs/phase-1-plan.md`, `docs/phase-2-plan.md` and the code on this branch. Every codebase fact cited below was checked in the repo (schema enums, `enqueueJob`, the runner's retry rule, the auth plugin's `readOnly`/role handling, `sync.ts`/`accounts.ts` balance writes, the plan loaders, `months.ts`/`dates.ts` helpers).

Where this document and an area design disagree, **this document wins** for the seam; where it is silent, the area design applies. The tie-break rule used throughout: prefer the definition that is more correct for a household owner reconciling the app to a brokerage statement, then the one that keeps a single implementation of each quantity.

Spec conflict carried forward by all four designs: the spec's data-sources table marks OFX/QFX as Phase 3 while its build-phase list puts OFX under Phase 6 Polish. OFX is out of scope for Phase 3; the import pipeline consumes `MappedPosition[]` / `MappedTrade[]`, so an OFX adapter is a parser only.

## 1. Reconciled decisions (binding over the four designs)

1. **One Fixed8 module**: `packages/shared/src/decimal.ts`. `Fixed8 = bigint` (×10⁸, unbranded). Exports: `parseFixed8`, `formatFixed8` (canonical, no trailing zeros), `roundDivHalfAway`, `mulToCents` (R1), `quantityForCents` (R2), `impliedPrice` (R3, on absolute values), `allocateLargestRemainder` (R4), `scaleQty` (R5), `fixed8ToCents`, `centsToFixed8`, `parseLooseDecimal`, `fixed8FromJsonNumber`, `percentToPpm`, `ppmToPercent`; Zod `Fixed8String = /^-?\d{1,12}(\.\d{1,8})?$/`, `NonNegFixed8String`; aliases `QuantityString = Fixed8String`, `PriceString = NonNegFixed8String`.
2. **Rounding, stated once.** Half away from zero (`roundDivHalfAway`) at exactly these sites: R1 quantity×price→cents, R2 cents÷price→quantity, R3 cents÷quantity→price, R5 split scaling per lot, `fixed8ToCents`, and the lot engine's basis consumption `roundDivHalfAway(B × take, Q)`. Cents allocated across pieces use largest remainder (R4). Every other integer division (bp, ppm, class splits, target cents, pro-rata gain estimates, averages) keeps Phase 2's truncation toward zero. Rates are floats, never stored, never fed back into cents.
3. **`investment_txn` columns and semantics**: the imports area's DDL and named CHECKs with these settlements: `sequence`; `fee_cents NOT NULL DEFAULT 0`; `amount_cents NOT NULL` (the importer derives it and records `derived`); unsigned `quantity` with `transfer_direction`; `split_num/split_den`; `cost_basis_cents`/`acquired_date` on transfer-in; `transfer_group_id` + `counterparty_account_id` (no `counterpart_txn_id`); **`ledger_transaction_id`** (not `transaction_id`) with a partial unique index; `external_id` `csvid:`/`inv:` (not `itx:`); `source ∈ csv | manual` now, `simplefin | ofx` reserved in the enum; `raw_description`, `memo`, `user_edited`; no `lot_selection` column (picks live in `lot_pick`). Same-day order is the lots area's `(date, type rank, sequence, id)` with split first.
4. **Reinvested dividends are two rows** (imports): `dividend` (+income, cash +) and `reinvest` (`amount_cents ≤ 0`, a purchase, cash −). The lot engine treats `reinvest` as a buy with basis `−amount` and cash effect `amount`, and never as income; `reinvestedCents` per month = Σ `−amount` of reinvest rows. The views area's "reinvest rows with `amount > 0`" branch is dropped.
5. **Lots**: derived cache rebuilt per account inside the writing transaction (`rebuildLots(tx, accountId)`); `lot` PK is a uuid kept stable by upsert on `(opened_by_txn_id, ordinal)` (a transfer-in leg that receives several source lots gets ordinals 0..n−1 with `origin_lot_id`); columns per the lots area (`opened_by`, `original_quantity`, `quantity`, `original_cost_basis_cents`, `cost_basis_cents`, `basis_known`, `closed_date`, `rebuilt_at`) plus `origin_lot_id`. Unknown basis = `basis_known = false` with basis 0 in the engine and `null` on the wire. `lot_pick(id, sell_txn_id, lot_id FK lot, quantity, position)` replaces jsonb selections. `lot_disposal` is the lots area's DDL (incl. `unmatched_sell`, `term`, `gain_cents`). Proceeds split by largest remainder; split scaling R5 per lot without a residual fix (the 0.001-share position tolerance absorbs it).
6. **Fidelity is derived, never stored**: `accountFidelities(db, accountIds)` in one service (`packages/db/src/services/accountFidelity.ts`) = the imports area's `hasTrades`/`hasSnapshots` + the lots area's `checkPositions` (0.001 sh) with the views area's rule (mismatch → `positions` + note). `account.investment_history` is **not created**; `account.lot_method` (fifo|specific), `account.cash_inference` (auto|off, **default `auto`**) and `account.investment_income_feed` are. The position check skips the cash security, securities with `asset_class = 'cash'` (sweep/money-market funds) and dollar-only rows.
7. **One valuation chain** (`valueAccountOn`, prices area) is the definition of an investment account's value on a date, for the Portfolio, Holdings, Allocation, dashboard investments block, reconcile preview, period/day change, and the performance engine's non-full-account valuation points. Cash is anchored the same way for every basis: `anchor` = latest *reported* `balance_snapshot` (source ≠ `computed`) on or before the date; `cash_plug = anchor.balance − Σ positions priced at anchor.date` (carried; > 0 → a labelled `Cash (from balance)` line, < 0 → `negative_residual` warning); transfers after the anchor are carried as cash. This is the lots area's D19 applied to positions accounts; it is on by default because the gate's statement total includes cash the positions feed usually omits.
8. **`balance_snapshot` rows with `source = 'computed'`** are written by a worker job `investments.valuation` (value from the chain, dates from the last reported row to the expected price date, `ON CONFLICT … WHERE source = 'computed'`) after every `prices.fetch`, positions commit, manual snapshot and reconcile commit. Phase 2's net worth stays on `balance_snapshot` unchanged and now agrees with the Portfolio on every date; the engine excludes computed rows from cash anchors but its loader feeds chain values for non-full accounts' boundaries.
9. **Day change** = price movement on today's quantities (prices area); **period change** = `change`, `netFlows` (lots area's external flows + opening values), `growth = change − netFlows` (one computation; the views area's `contributionsCents`/`growthCents` names map onto `netFlowsCents`/`growthCents`, plus its `incomeCents` and `uncategorizedRows`).
10. **External flows**: one loader `loadExternalFlows` (lots area) = posted ledger `is_transfer` rows ∪ `investment_txn` cash transfers, where a cash row is dropped when `ledger_transaction_id IS NOT NULL` **or** an equal-amount ledger transfer within 3 days exists; securities transfers at market; opening values; each flow carries `source ∈ ledger | investment_txn | engine`.
11. **Income**: one route `GET /api/investments/income` (views area) built on the lots area's pure `incomeByMonth(txns)`; `household_setting.dividends_as_income` is dropped in favour of `investment_income_category_id` + per-account `investment_income_feed`. Months carry `feesCents` too.
12. **Reconciliation**: the prices area's `account_reconciliation` table, preview/commit/history routes and two-part gate (pre-commit within $1, post-commit exact) plus a `DELETE /api/reconcile/:id`; audit entity `account_reconciliation`; `matchesToDollar = |diff| < RECONCILE_TOLERANCE_CENTS (100)` everywhere (imports preview, reconcile, dashboard). The views area's reconcile table/routes are dropped; its "why did it change" endpoint stays.
13. **Routes and files**: imports → `routes/securities.ts`, `routes/investmentTxns.ts`, additions to `routes/import.ts`; lots → `routes/performance.ts` (`POST /performance`, `GET /lots`, `GET /realized`, `PUT /txns/:id/lot-picks`, `POST /lots/rebuild`); prices → `routes/prices.ts`, `routes/valuation.ts`, `routes/reconcile.ts`; views → `routes/investmentViews.ts`. One `PATCH /api/investments/securities/:id` (pricing fields trigger `updateSecurityPricing`); manual prices only at `PUT/DELETE /api/prices/:securityId/:date`.
14. **Jobs**: `JobType` += `simplefin.reprocess_holdings`, `prices.fetch`, `investments.valuation`, `investments.income_feed`; `enqueueJob` gains `payload.dedupeKey`; every price refresh goes through `requestPriceRefresh`; the runner retries unless `err.permanent === true`.
15. **Enums unified**: `InvestmentFidelity = balance_only | positions | full_history` (the lots area's `InvestmentHistoryLevel` and the prices area's `InvestmentLevel` are gone; "none" is `null`); `HoldingPriceSource = provider | implied | manual | statement | txn | cash`; `LineKind = position | cash | cash_plug | carried_flows`; `InvestmentPeriod = 1w | 1m | 3m | 6m | ytd | 1y | 3y | 5y | all | custom` with one `periodStart`; `AuditEntity` += `security, investment_txn, holding_snapshot, allocation_target, lot_pick, account_reconciliation, account`; `TransactionSource` += `investment`.
16. **`holding_snapshot`** is the imports area's DDL (nullable `quantity`, `price`, `reported_cost_basis_cents`, `source ∈ simplefin | csv | manual`). **`price`** is the imports DDL plus the prices area's `adj_close`, `provider`, `suspect`, `fetched_at` and `price_provider_shape` CHECK; `close >= 0`; no `provider_adjusted` source. **`security`** carries `expense_ratio_ppm integer`, the prices area's fetch-state columns, `always_price`; money-market/sweep funds default to `price_mode = 'implied'`.
17. **`household_setting`** gains `benchmark_security_id`, `investment_income_category_id`, `rebalance_band_bp`, `rebalance_min_trade_cents` (not `dividends_as_income`). `AccountView` gains `investment: { fidelity, fidelityNote, positionsMatch, lastSnapshotDate, lastSnapshotSource, lastTradeDate, securityCount, needsReviewCount, lastReconciliation }`, `lotMethod`, `cashInference`, `investmentIncomeFeed`.

## 2. Conflicts and resolutions

Format: areas · issue · resolution · reason.

### 2.1 Numeric representation and rounding

**C1. Fixed8 module name and function names.** imports (`decimal.ts`: `roundDiv`, `mulToCents`, `impliedPrice`, `fixed8ToCents`, `DecimalString` unbounded), lots (`fixed.ts`: `roundDivHalfAway`, `mulQtyPrice`, `divCentsByPrice`, `basisPerShare`, `scaleQty`, `allocateLargestRemainder`, `Fixed8String` bounded), prices (imports' names, wants the bounded string), views (`roundHalfAway`, `mulToCents`, `quantityForCents`, `impliedPrice`). Resolution: Decision 1 (`decimal.ts`; `roundDivHalfAway`, `mulToCents`, `quantityForCents`, `impliedPrice`, `scaleQty`, `allocateLargestRemainder`; bounded `Fixed8String`). Reason: one module, the most descriptive name for each rule (the rounding exception to Phase 2 must be visible in the name), and the bounded regex is the exact image of `numeric(20,8)`.

**C2. `formatFixed8` canonical form.** imports/prices: no trailing zeros (`"12.5"`); lots: always eight places (`"123.40000000"`). Resolution: no trailing zeros; tests compare through `parseFixed8`, never text. Reason: two areas and the wire contract already assume it; Postgres accepts either on write. The lots area's TC1 expectation `"123.40000000"` becomes `"123.4"`.

**C3. `amount_mismatch` threshold.** imports mapper: `max(100, |A|/100)`; lots engine: 5 cents. Resolution: 5 cents, one pure helper `amountMismatch(q, p, fee, amount)` used by the trades preview and the engine. Reason: a brokerage confirmation reconciles to the cent; a $1/1 % band would hide a mis-mapped fee column, which is exactly what the preview should catch.

**C4. Proceeds split across lots.** imports: "cent remainder on the last lot"; lots: largest remainder (R4). Resolution: largest remainder. Reason: stated, tested (TC2/TC22), and it is how a 1099-B allocates.

**C5. Split scaling.** imports: truncate per lot to 8 decimals, residual on the latest lot so Σ is exact; lots: `scaleQty` half-away per lot (R5), no residual. Resolution: R5 per lot. Reason: one rounding site; brokers round fractional split shares per lot (cash in lieu); the 0.001-share position tolerance absorbs 10⁻⁸ drift.

### 2.2 Tables and columns

**C6. `investment_txn` DDL.** imports vs lots differ in column names (`sequence`/`seq`, `split_num`/`split_numerator`, `cost_basis_cents`/`basis_cents`, `acquired_date`/`basis_acquired_date`, `transaction_id`/`ledger_transaction_id`, `raw_description`+`memo`/`description`+`notes`), nullability (`amount_cents`, `fee_cents`), quantity sign (unsigned + `transfer_direction` vs signed), pairing (`transfer_group_id`+`counterparty_account_id` vs `counterpart_txn_id`), picks (`lot_selection` jsonb vs `lot_pick`), ids (`inv:`/`csvid:` vs `itx:`), CHECKs (named per type vs one `investment_txn_shape`). Resolution: Decision 3. Reason: the imports area owns the writers, the API body and the preview, and its named CHECKs give readable failures; `amount_cents NOT NULL` because the importer already derives it with the engine's own formulas (the engine's null branch is dead code); `ledger_transaction_id` because two areas and an index name use it and it says what it links; the lot engine's `loadInvestmentTxns` applies the sign (`sell` and `transfer out` → negative) so the engine's internal signed convention is unchanged.

**C7. Specific-lot identification.** imports: `investment_txn.lot_selection jsonb [{lotId, quantity}]`, Σ = row quantity, codes `lot_not_found | lot_insufficient | lot_selection_sum`; lots: `lot_pick` table, Σ ≤ sale with FIFO for the remainder, `PUT /txns/:id/lot-picks`, audit entity `lot_pick`, codes `not_a_sale | pick_security_mismatch | picks_exceed_sale | pick_exceeds_lot`. Resolution: `lot_pick` keyed by `lot_id` (FK to the stable lot id), the lots area's route, validation and codes plus `lot_not_found`; `CreateInvestmentTxnBody.lotSelection` becomes `lotPicks` and is written as `lot_pick` rows in the same request. Reason: a real FK survives rebuilds and cascades correctly; jsonb cannot be validated by the database; the engine's warnings (`pick_unavailable`) replace the imports area's `lot_selection_cleared`.

**C8. Lot identity.** imports: uuid PK stable by `(opened_by_txn_id, ordinal)`; lots: `lot.id = opening txn id` (one lot per opening row, multi-lot transfers mirrored as several transfer-in rows). Resolution: Decision 5 (uuid + ordinal). Reason: an own-account in-kind transfer of a position held in several lots is one row per leg in the file and in the manual form; the ordinal keeps one lot per source lot with its acquisition date without inventing rows. `rebuildLots` runs the out-leg's account first, then the in-leg's account reads the counterparty's `transfer_out` disposals for the group.

**C9. Unknown basis representation.** imports: nullable `cost_basis_cents`; lots: NOT NULL 0 + `basis_known`. Resolution: lots' representation in the table and engine, `null` on the wire. Reason: the engine's conservation invariants need total integer arithmetic; the API must not show a fake zero.

**C10. `lot_disposal` DDL.** imports (minimal) vs lots (adds `account_id`, `security_id`, nullable `lot_id` for `unmatched_sell`, `acquired_date`, `gain_cents`, `term`, `basis_known`). Resolution: the lots DDL; the unique index is on `(close_txn_id, COALESCE(lot_id, '00000000-0000-0000-0000-000000000000'))`. Reason: realized gains and the Phase 4 tax engine read these per disposal.

**C11. `holding_snapshot` DDL.** lots: `quantity NOT NULL`, `cost_basis_cents`, `source` incl. `simplefin_extra`; imports/views/prices: nullable `quantity`, `reported_cost_basis_cents`, `simplefin|csv|manual`. Resolution: imports. Reason: dollar-only 401(k) positions must be stored, not rejected; the statement's basis is "reported".

**C12. `price` DDL.** lots: `close > 0`, `source` incl. `provider_adjusted|csv`; imports: `close >= 0`, three sources; prices: adds `adj_close`, `provider`, `suspect`, `fetched_at`. Resolution: Decision 16. Reason: a delisted security closes at 0; adjusted closes belong on the same row so one series serves valuation (unadjusted) and the benchmark (adjusted when present, `adjusted: boolean` reported).

**C13. Expense ratio.** lots: `numeric(8,6)`; imports/views: `expense_ratio_ppm integer`. Resolution: ppm. Reason: 0.035 % = 350 ppm is exact; the weighted ratio becomes integer math; the lots area's objection was to basis points, not ppm.

**C14. Fidelity: stored vs derived.** lots: `account.investment_history` (stored, raised by imports, user-settable); prices: needs the stored flag for the lots-as-basis switch, else proposes `account.position_source`; imports and views: derived. Resolution: Decision 6. Reason: "full history" must mean the lots explain the latest statement; a derived level with the position check already prevents the prices area's $157.63 case (one post-statement reinvest makes the lots mismatch, so the statement stays the basis) and cannot go stale; a stored flag would say "full" while the lots cover 20 of 40 shares. The lots engine's `history` input and the valuation chain's lots step both read the derived value.

**C15. Reconciliation table and routes.** prices: rich `account_reconciliation` (basis, rows, accepted, several rows per date), `POST /reconcile/preview|commit`, `GET /reconcile/history`, audit entity `reconciliation`; views: minimal table unique per `(account, date)`, `GET/POST /investments/accounts/:id/reconcile`, `DELETE /investments/reconciliations/:id`, audit entity `account_reconciliation`. Resolution: Decision 12. Reason: the prices area's preview compares row by row and can accept the statement as the snapshot, which is what makes the gate repeatable; evidence rows must keep failed attempts; the entity name should be the table name as in Phase 2.

**C16. `household_setting` additions.** imports: `benchmark_security_id`, `dividends_as_income`; views: `investment_income_category_id`, `rebalance_band_bp`, `rebalance_min_trade_cents`. Resolution: Decision 17. Reason: a boolean cannot name the category or decide whether the app creates rows for CSV-only accounts; the per-account feed does.

**C17. `AccountView.investment.reconciled` name clash.** imports: `reconciled` = lots match the latest snapshot; prices: `reconciled` = `account_reconciliation.reconciled` (within tolerance of a statement). Resolution: `positionsMatch: boolean | null` for the lots check, `lastReconciliation` for the statement check. Reason: two different facts with the same name would mislead the badge.

**C18. Account columns.** lots: `investment_history`, `lot_method`; prices: `cash_inference` (default off); views: `investment_income_feed`. Resolution: `lot_method`, `cash_inference` default **`auto`**, `investment_income_feed`; no `investment_history`. Reason for the default: the gate's statement total includes sweep cash that SimpleFIN `extra` and many positions CSVs omit; with the plug off every such account fails the gate by its cash; the plug is labelled and the reconcile preview still shows both settings.

### 2.3 Definitions of the same quantity

**C19. "Account value".** views: latest `balance_snapshot` any source (expects a `computed` writer); prices: chain snapshot → lots → repriced positions → balance → null, no computed rows (OQ4); lots: priced lots + anchored cash for full accounts, reported balances (fallback Σ snapshot) for others. Resolution: Decisions 7 and 8. Reason: one function defines value; anchoring cash on the latest reported balance is already the lots area's rule and makes the positions basis equal the Bridge's balance on every reported date (so net worth and Portfolio agree) while repricing between statements for CSV-only accounts; the derived `computed` rows keep Phase 2's net worth untouched.

**C20. "Holding value".** views D5: statement value unless a strictly newer price; prices: statement on the snapshot date, repriced after. Same rule; the chain's lines are the only source for the Holdings page (quantities from the chain, which picks lots or statement per account; cost basis from `computeHoldings`). Reason: one quantity per line.

**C21. "Cost basis".** lots engine (FIFO/specific, fees included) vs statement `reported_cost_basis_cents`. Resolution: `basisSource ∈ lots | statement` (views); gains only from lots (spec). No conflict, recorded for completeness.

**C22. "External flow".** imports: ledger transfers ∪ unlinked cash rows (dedupe by link); lots: ∪ cash rows deduped by amount within 3 days, securities transfers at market, opening values; prices/views consume the lots loader (views wants a `source` field). Resolution: Decision 10. Reason: the link is exact; the heuristic covers the window before `linkUnlinkedInvestmentTxns` runs; in-kind transfers are capital entering the account (GIPS).

**C23. "Day change".** views: Δ of balance snapshots (includes deposits); prices: price-only on today's quantities, balance-only accounts null and the total marked partial. Resolution: prices. Reason: a Saturday HSA deposit is not a market move; the views area's "why did it change" decomposition (price effect + quantity effect + residual + flows) covers arbitrary windows and stays.

**C24. "Period change".** prices (`changeCents`, `netFlowsCents`, `marketChangeCents`, `flows_not_in_value`) vs views (`contributionsCents`, `growthCents`, `incomeCents`, `uncategorizedRows`, start = latest snapshot ≤ from). Resolution: Decision 9 (one computation; views' names mapped). Reason: the same number must not be computed twice from different start values.

**C25. "Income".** lots: engine `buildLots(...).income` with its own `GET /api/investments/income`; views: same path, ledger union, link state, feed; imports: `dividends_as_income`. Resolution: Decision 11. Reason: one route per page; the engine's aggregation stays a pure, tested function; fees belong in the month because statements list them.

**C26. "Staleness".** lots: `stale_price` 7 calendar days (engine warning); prices: trading days against the expected close, keyed on `price_mode`; views: `priceStale` 7 d, `valuationStale` 7 d, `positionsStale` 35 d. Resolution: user-facing price status = prices' `PriceStatus`/`tradingDaysBehind`; views' `priceStale` = `priceStatus === 'stale'`; views' account-level `valuationStale`/`positionsStale` stay; the engine's `stale_price` stays an engine warning. Reason: a long weekend must not flag Thursday's close; statement-dated prices are "as of", not stale.

**C27. "Matches to the dollar".** imports `matchesToDollar` (`|diff| < 100`), prices `matchesToTheDollar`, views "matches the statement" (0) / "to the dollar" (< $1). Resolution: `matchesToDollar` with `RECONCILE_TOLERANCE_CENTS = 100` in `packages/shared`; 0 is shown as "exact". Reason: one gate rule.

**C28. Fidelity enum.** `InvestmentHistoryLevel` (lots), `InvestmentLevel` incl. `none` (prices), `InvestmentFidelity` (imports/views). Resolution: `InvestmentFidelity`, null for non-investment types. Reason: one word per level.

**C29. Price-provenance enums.** prices: `priceSource provider|implied|manual|fixed` + `priceStatus statement`; views: `HoldingPriceSource provider|implied|manual|snapshot|cash`; lots: `price|txn|cash`. Resolution: Decision 15 (`HoldingPriceSource = provider|implied|manual|statement|txn|cash`; the engine's price series points carry the row's `source`). Reason: a price taken from a transaction is neither a statement price nor an implied one and must say so.

**C30. Line kinds.** prices: `position|cash|cash_plug|carried_flows`; views: `position|cash|residual`. Resolution: prices' kinds; the views area's "Cash (unlisted)" line is `cash_plug` labelled "Cash (from balance)". Reason: the plug and carried flows are different explanations and the reconcile preview shows them separately.

**C31. Period presets.** three overlapping sets. Resolution: Decision 15, one `periodStart` (prices' and views' definitions agree: `addMonthsClamped`, YTD = Dec 31, all = earliest data / inception).

### 2.4 Functions one area calls that another does not provide (or provides differently)

**C32. `rebuildLots` signature.** imports calls `rebuildLots(tx, accountId, securityId)`; lots provides `rebuildLots(tx, accountId)`. Resolution: per account. Reason: simpler, O(n log n) per account, and transfers between securities' lots never cross; `touchedPairs` becomes `touchedAccounts` (out-leg accounts first, C8).

**C33. `reconcileHoldings(db, accountId, date) → boolean`** (imports expects) vs `checkPositions(positions, snapshot) → EngineWarning[]` (lots provides). Resolution: `checkPositions` inside `accountFidelities`; `positionsMatch = warnings.length === 0` (null without a snapshot). Reason: one check, reused by the badge, the lots route and the performance warnings.

**C34. `writeImpliedPrices` tie rule.** prices requires a deterministic same-date rule (largest `value_cents`, then `account_id`) that the imports area's per-import writer cannot honour. Resolution: `writeImpliedPrices(tx, date, positions)` is implemented as `rebuildImpliedPrices(tx, { securityIds, dates })` reading every `holding_snapshot` row for the pair. Reason: idempotent and order-independent.

**C35. Price refresh enqueue.** imports: `enqueueJob('prices.fetch', { reason }, { dedupe: true })`; prices: `requestPriceRefresh({ reason })` with `dedupeKey`. Resolution: `requestPriceRefresh`. Reason: type-level dedupe would be swallowed by a queued continuation.

**C36. `loadExternalFlows` shape.** lots: `(db, accountId, from, to)`; prices: `(db, accountIds, from, to)`; views wants `source`. Resolution: `(db, accountIds, from, to) → ExternalFlowInput[]` with `accountId` and `source` on each flow.

**C37. `computeHoldings` / lots drawer vs Holdings page quantities.** views merges engine rows (full accounts) with snapshot rows (positions accounts); the chain already decides per account. Resolution: C20. Reason: one quantity per line.

**C38. Performance read: GET (views, presets) and POST (lots, `readOnly`, `detail=full`).** Both stay: the GET presents, the POST backs "how this was computed"; the GET takes `accountIds` as a comma-separated string (prices' convention). Reason: Phase 2's `readOnly` POST precedent is verified in `plugins/auth.ts`; a presentation route must equal the engine route (views test 12 asserts it).

**C39. Manual price route and securities pricing route.** imports: `POST /investments/securities/:id/prices`; prices: `PUT/DELETE /api/prices/:securityId/:date` and `PATCH /api/securities/:id/pricing`. Resolution: Decision 13. Reason: one path per fact; `/api/securities` is not where the securities routes live.

**C40. Positions import balance.** imports writes `balance_snapshot = Σ positions` for non-fed accounts, so a CSV-only account's plug is always 0 and its cash never appears unless the file lists it. Resolution: `PositionsCommitBody` and `ManualPositionsBody` gain optional `statementTotalCents`; the balance row = `statementTotalCents ?? Σ positions`. Reason: the statement's total is the number the owner reconciles to; the difference is its cash.

**C41. `balance_snapshot` precedence.** prices' reconcile commit writes a `manual` balance row for the statement date; `upsertSimplefinAccount` (verified) overwrites `balance_snapshot` unconditionally with `source = 'simplefin'`. Resolution: the sync's balance upsert gains `WHERE balance_snapshot.source <> 'manual'`; the imports area's snapshot precedence (manual > csv > simplefin) applies to balance rows too. Reason: a hand-checked statement must survive the next 6-hour sync. Flagged as a Phase 1 touch (§4).

### 2.5 Duplicated responsibilities

**C42. Two valuation implementations for positions accounts** (views' loader `valuations`/`valueHolding`/`accountPicture` vs prices' `valueAccountOn`). Resolution: prices' engine only; `investmentContext` calls `loadValuationInput` + `valueAccountOn`. Reason: C19.

**C43. Two reconcile screens** (views' `ReconcilePanel` on the Portfolio row vs prices' Reconcile page). Resolution: the Reconcile page; the Portfolio row links to it with `accountId` and the latest statement date. Reason: one flow writes the evidence.

**C44. Two routes/files named `routes/investments.ts` and `views/investments.ts`** (imports and lots). Resolution: Decision 13.

**C45. Two sets of import-time reconciliation lines** (imports' positions preview `knownBalanceCents`/`differenceCents` vs prices' reconcile preview). Both stay (different moments: before writing a snapshot vs checking the app against a statement) and share `matchesToDollar`.

**C46. `PATCH /investments/securities/:id { assetClass }`** (imports) and **`PUT /investments/securities/:id/allocation`** (views, sets class and splits). Resolution: both; the PATCH refuses a class not among existing splits (`400 split_primary`).

**C47. Dashboard blocks.** prices: optional `prices` block; views: `investments` block. Resolution: one `investments` block carrying the views area's fields plus `priceFeed: { configured, expectedDate, stale, notFound, error }` from `priceFeedHealth`.

### 2.6 Names, error codes, enums, jobs

**C48. Engine warning codes.** imports: `oversold | lot_selection_stale | unknown_basis`; lots: `oversell | pick_unavailable | basis_unknown`. Resolution: lots' `EngineWarningCode`.

**C49. Error codes.** 404s: imports' `security_not_found`/`snapshot_not_found` vs `not_found` (prices, views). Resolution: `not_found` with the entity named in the message, as Phase 2 routes do. Union of the remaining codes is kept (each area's codes for the routes it owns); `viewer` and `today_out_of_range` come from the existing plugin and `resolveToday`.

**C50. Audit entities.** `reconciliation` (prices) vs `account_reconciliation` (views). Resolution: `account_reconciliation` (Decision 15).

**C51. Job types and the daily tick.** views assumes `investments.valuation` of the prices area (which did not design it) and an ordered tick `prices.fetch → investments.valuation → recurring.detect → investments.income_feed → plan.close_month`; prices schedules nightly/catch-up at household-local hours; the existing tick (`DAILY_JOB_TYPES`) fires at `DETECT_HOUR_UTC`. Resolution: `investments.valuation` is chained from the end of every `prices.fetch` run (and enqueued after positions commits, manual snapshots and reconcile commits, deduped by key); `DAILY_JOB_TYPES = ['recurring.detect', 'investments.income_feed', 'plan.close_month']`; `schedulePriceJobs` stays separate. Reason: the valuation must follow the prices it uses, not a clock.

**C52. `ingestTransactions` signature** (imports widens to `DbOrTx`, adds `accountType`) and the views area's synthetic rows (`source = 'investment'`): compatible; both land in step 7 of the build order.

**C53. Period/asOf query shapes.** prices: `date`, `period`, `accountIds` string; views: `asOf`, `period`, `from/to`; lots: body. Resolution: `asOf` everywhere a date is meant (prices' `date` → `asOf`); `accountIds` comma-separated on GETs. Reason: one name for the same parameter across the Investments pages.

## 3. Gaps against the spec's Phase 3 scope and gate

G1. **"Contributions from paychecks or transfers into investment accounts are recognized as transfers and counted toward savings goals, which gives the retirement planner your real savings rate rather than an estimate."** Covered for SimpleFIN-fed accounts (the imports area's ingest classifier) and for trade-file cash rows in CSV-only accounts (ledger rows). Uncovered: a 401(k) with no transaction feed (balance-only, or positions by CSV) whose payroll deferrals never appear in any ledger: goals and XIRR never see them (lots OQ1). Resolution for Phase 3: the imports area's manual cash `transfer` into a non-SimpleFIN-fed account also creates the ledger row (the same path as trade-file cash rows), so a hand-entered contribution reaches goals; synthesizing flows from the recurring item with `transfer_account_id` is deferred to Phase 4 (the planner's savings rate) and recorded as an open question.

G2. **Level table, Balance only: "contributions estimated from cash transfers in".** No design estimates contributions for a balance-only account from the *checking* side when the investment account has no feed. Covered in practice by Phase 1 pairing when both legs exist and by G1's manual row otherwise; the Performance page shows `flowsSource: none` so the owner knows. No further work in Phase 3.

G3. **"fetched once a day after market close for held securities only".** The prices area runs nightly plus a conditional catch-up and also fetches the benchmark and `always_price` securities. Accept, flagged (a fund NAV posts late; a benchmark cannot be "held").

G4. **Gate: "account values match brokerage statements to the dollar on a chosen date".** Each area has a piece (imports' preview line, prices' two-part gate and test 19, views' recorded check). Gap: no single end-to-end gate test exists across areas. Resolution: `packages/db/src/services/investmentsGate.test.ts` (step 13): positions CSV → implied prices → nightly fetch (fake provider) → reconcile preview within $1 → commit → post-commit exact → dashboard `awaitingReconcile` 0, run on both the prices area's S1 and the views area's INV seed; the owner's own statement is the acceptance step as in Phases 1 and 2.

G5. **"Prices come through a provider interface (one free end-of-day source to start, swappable)" / open question "check current terms as of October 2026".** The prices area chose Tiingo but could not verify terms from the build container. Gap: the terms check is a human step before the first fetch; `.env.example` must say so. Carried as an open question.

G6. **"value-over-time line from `balance_snapshot` and `holding_snapshot`".** Covered by the chain only once the `computed` rows exist (Decision 8) or by `valueSeries`; the Portfolio uses `GET /api/valuation/series` (not a second series built from balance rows).

G7. **Spec data-model row `investment_txn … type (… transfer)`** is satisfied; **`interest`** is an addition flagged by all areas. **`security.type` gains `other`**; flagged.

G8. **Multi-currency.** Every area assumes USD; the spec's `security` row has no currency. Not a Phase 3 gap; shared open question (a non-USD holding is a preview warning).

G9. **Securities sold before Phase 3 went live** are never priced automatically (prices OQ7), so realized-gain views for old sales lack prices. Resolution: the fetch set includes any security with a `lot_disposal` dated within 400 days; otherwise `POST /api/prices/refresh { securityIds }`.

## 4. Contradictions with binding Phase 1/2 decisions, and Phase 1/2 code touched

Contradictions (each resolved):

P1. **Phase 2 "bigint division truncates toward zero" (binding)** — all four areas round half away for R1–R3 (and R5, basis consumption). Resolved as a stated exception list (Decision 2); no truncation anywhere else.

P2. **Phase 2 §15 "net worth from `balance_snapshot`"** — the views area's D3 kept it but assumed a `computed` writer the prices area declined (OQ4), and the prices area's chain would have put the Portfolio and net worth on different numbers. No migration backfill of `on_budget` (the Accounts page offers the one-click move).

P4. **Phase 1 sync "user fields never updated by the sync"** — the views area's income feed sets `category_id` on bank rows from a worker job. Resolved: it behaves like the rules engine (unlocked only, never when `category_locked`), triggered by the owner's explicit per-account setting.

P5. **Phase 1 transfer pairing "candidates are unpaired transactions in the user's own accounts"** — the views area excludes synthetic feed rows and rows linked to income `investment_txn` rows; the imports area marks unpaired contributions `is_transfer = true` at ingest. P6. **Phase 1 `upsertSimplefinAccount` unconditional balance upsert** — C41 adds `WHERE source <> 'manual'`.

P7. **Phase 2 §17 job dedupe (`enqueueJob`, verified: type + `connectionId`)** — the prices area adds `payload.dedupeKey`; existing callers unchanged. Phase 1 runner retry rule (verified `SimplefinError.permanent`) generalised to any `permanent === true`.

P8. **Phase 2 §16 today** — every route uses `resolveToday`; the prices area's `expectedThrough` uses the server clock in America/New_York (a market fact, not the household's day). Consistent.

P9. **Phase 1 "the worker is the only container that talks to the outside world"** — Tiingo is called from the worker only; the API reads `PRICE_PROVIDER` from env to render state (compose's shared `env_file` verified). Consistent. Key via env/secret file, never the database (CLAUDE.md).
